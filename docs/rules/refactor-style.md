# 重构风格规则

重构应降低理解和修改成本：执行路径更直接、职责更清楚、状态与副作用更显式。只搬动代码或增加层级，不算改善。

## 1. 判断标准

- 服务当前真实需求，不为假想复用或扩展提前建立通用模型、框架和层级。
- 顺着业务流程就能读懂入口、分支和结果，减少跨函数、跨文件跳转。
- 名称、参数和数据结构明确表达语义；依赖、执行条件及边界行为不靠隐含约定。
- 少量重复优于错误抽象。逻辑相似但语义、上下文或变化方向不同，保持分别实现。

## 2. 拆分与内联

- 有独立业务含义、多个语义一致的调用点，或细节明显打断主流程时，才提炼函数。
- 短小、直白、单调用点且无独立语义的逻辑留在调用处，不为缩短行数拆分。
- 提炼后的名称应说明行为；若仍需跳进实现才能理解，只是移动了复杂度。
- 不为消除几行重复增加大量参数，不让简单流程依赖一套新框架。

## 3. 数据与状态

- 直接从输入构造结果，只在必要边界转换，避免先包装成通用结构、下游再拆回业务结构。
- 不为局部数据新增中间模型；统一结构不能让同一字段在不同场景承担不同含义。
- 不向外暴露内部可自行管理的中间状态，不用额外状态弥补职责划分问题。
- 不叠加兜底和重复校验来掩盖已有契约，应修正负责该约束的边界。

## 4. 副作用

- 状态更新、写入、删除、外部调用和日志应在主流程中显式调用，与触发条件就近放置。
- 函数命名和调用处应能看出实际动作，不让普通查询或转换暗中修改状态。
- 不把关键状态变化藏在深层封装、默认分支或兜底逻辑中。

## 5. 优先删除的结构

- 只改名或透传，没有独立语义、未隔离真实复杂性的中间层。
- 只把已有数据再包一层、没有明确用途的类型。
- 短小直白且只有一个调用点的包装函数。
- 仅为弥补设计问题存在的中间状态。
- 让业务语义模糊、调用方需要额外记忆规则的统一模型。
- 已不再需要的兼容分支。

## 自查

- 解决的是当前问题，还是假想的通用性？
- 提炼出了独立职责，还是只把代码搬走？
- 删除中间层或保留少量重复，是否更容易理解？
- 数据语义是否清楚，状态和副作用是否在主流程中可见？
- 新增概念带来的收益，是否大于理解成本？
