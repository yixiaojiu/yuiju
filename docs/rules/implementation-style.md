# 代码规范

以长期维护为目标：职责清楚、顺序可读、状态唯一、副作用显式。减少理解成本，不追求形式上的抽象和统一。

## 1. 整体设计

- 先看完整调用链、状态归属和执行位置，再决定改动落点，避免只解决当前函数的局部问题。
- 新能力沿用同类能力的组织方式；只修改当前需求必要涉及的链路，不顺手重构或提前设计未来框架。
- 必须调整模块边界时，先说明原因、范围和收益。

## 2. 模块划分

- 按业务职责和共同变化的原因组织模块，同类能力的定义与执行入口集中维护。
- 业务逻辑放所属应用；shared 放实际共用的技术能力及项目约定集中维护的提示词。
- 主流程负责调度，能力模块负责执行，状态由所属模块管理。例如工具 schema 与执行入口归工具模块，规划轮次与行动选择归 Planner。
- 不建空模块或纯透传中间层，也不把不同职责集中成一个大文件。

## 3. 函数可读性

- 按执行顺序和业务阶段展开，输入处理、状态判断、外部调用、结果处理分段清楚；关键判断与副作用就近放置。
- 短小、直白、单调用点的逻辑优先内联；具有独立职责、稳定复用或明显打断主流程的细节才提炼函数。
- 不为缩短行数拆函数，也不让主流程变成难以理解的 helper 调用链；调用处应看得出输入、结果和关键副作用。

## 4. 过度抽象

- 新增函数、类型、字段或模块必须有明确语义；复用已有领域概念，不为局部临时数据建立复杂类型或泛型体系。
- class 用于需要实例身份、状态或生命周期的对象；无状态计算和单次执行优先用函数，不为容纳几个方法创建实例。
- 少量重复优于错误抽象；不为消除几行重复引入复杂参数、中间层或扩展框架。
- 无独立职责的组件、纯透传函数和无实际用途的类型，合并或删除。

## 5. 状态与变量

- 一个事实只存一份，其余按需派生；必要冗余必须明确真相源，不用相近字段互相兜底。
- 只有跨调用保留的信息才成为实例状态，并明确创建、更新和清理位置；临时数据留在局部。
- 不为访问方便重复保存模型实例、整份配置或可推导数据。删除无助理解的中间变量，保留能解释业务含义的变量。
- 状态过多时先检查重复数据和职责混杂，不靠注释掩盖复杂度。

## 6. 异步写法

- 优先 `async/await` 和 `try/catch/finally`，少用 `.then/.catch` 链或层层 Promise 回调。
- 有依赖的步骤顺序 `await`；独立且适合并发的步骤用 `Promise.all`，不强行串行或并发。
- 队列、锁和后台任务必须明确等待对象、占用与释放时机，以及异常结束方式。
- 应用入口显式调用具名 `main()`，启动步骤放在函数内；不使用顶层 await 堆放启动逻辑，不写同步或异步自执行函数。

## 7. 命名

- JS/TS 函数和变量用 camelCase，class 和类型用 PascalCase；外部协议与配置字段遵循既定契约，命名转换在入口完成。
- 名称准确表达职责和业务含义，同义同名、异义区分，不使用晦涩缩写或过大的概念。
- 特殊用途体现在名称中，例如 `formatLlmDateTime`，避免用 `format` 暗示通用能力。

## 8. 注释

- 解释目的、约束、取舍、步骤依赖和非显然副作用，不复述代码。
- 声明需要说明时使用 `/** ... */`，便于 hover 阅读；按需交代参数含义、单位、可选行为和返回值。
- 直白代码不强加注释；需要长篇解释才能读懂时，先检查命名和设计。

## 9. 显式边界

- 配置、阈值、外部调用、写入和状态变化在调用处可见，不依赖隐藏环境变量或未约定行为。
- 内部接口按明确契约使用，不用重复校验、兼容分支、默认值或 catch 后回退掩盖错误；输入不符时修正上游契约，让错误正常暴露。
- 不自行增加降级行为；业务明确要求时，说明适用边界。

## 自查

- 职责、调用链和改动范围是否清楚？
- 主流程能否顺着读懂，是否过密或跳转过多？
- 新增抽象和状态是否必要，能否删除中间层或重复数据？
- 副作用、异步生命周期和错误处理是否显式？
- 命名是否准确，文档注释是否说明了关键约束？
