# 聊天回复训练数据收集方案

> 原始采集已实现；标注、模型辅助审核与数据导出待实现。

## 目标与范围

从线上真实聊天中收集 Replyer 的输入与回复，人工判断回复质量，保留合适的回复或改写不合适的回复，积累可长期保存的训练数据。未来使用这些数据微调聊天回复模型，替换 Replyer 调用的模型。

第一版聚焦 Replyer 的表达质量及本次是否输出回复，不训练 Planner 的触发与工具决策，也不接入实际模型训练流程。

预期微调后直接替换当前 Replyer 调用的模型，保留现有调用方式。采集与训练使用 Replyer 实际收到的完整上下文，不单独设计精简输入格式，也不裁剪成“最后一句话 → 回复”。

一次人工审核同时积累 SFT（监督微调）和 DPO（偏好训练）数据。两类数据共用同一份采集与标注记录，导出时分别生成数据集；同时收集不代表必须同时训练，训练顺序和效果对比后续确定。

质量判断沿用聊天测评方向：

- 是否符合当前上下文，有没有突兀接话或答非所问。
- 是否像真实的人在网上聊天，避免机械台词和表演感。
- 是否符合悠乃的人设与交流边界，避免套路化关心和不必要的亲密表达。
- 是否尊重输入中的事实，不随意编造生活经历。

## 样本单位与采集位置

一条样本对应一次 Replyer 生成，不对应一条 QQ 消息。一次生成可能拆成多条消息发送，训练目标使用拆分前的完整回复；模型明确选择不回复时也保留原始输出。

### Replyer 输出约定

- 正常回复直接输出正文，不包裹 XHTML 或其他标签。
- 去除首尾空白后，全文等于 `[[NO_REPLY]]` 表示主动不回复。普通正文中的方括号或嵌入的标记不触发控制逻辑；后续控制语义按需沿用 `[[大写语义名]]`，当前只实现这一种。
- 主动不回复作为正常工具结果告知 Planner，不发送消息、不记录发送事实、不标记失败。真正的空输出、截断与请求异常仍按生成失败处理。
- @ 和引用由程序附加；Replyer 的临时 @ 上下文用自然语言说明。模型正文中的消息协议标签在 Replyer 出口判为格式错误，不解析成平台操作，也不静默删除后发送。
- 原始采集保留正常结束且非空的模型输出，包括 `[[NO_REPLY]]` 和含错误协议标签的正文，便于后续审核纠正；没有自动进入训练集的路径。训练输出沿用相同约定，确认后的沉默样本以 `[[NO_REPLY]]` 为目标。

当前 Replyer 的输入不只有群聊记录，还包括：

- 公共人设、通用回复规则和角色专属回复提示词。
- 压缩摘要及尚未压缩的聊天历史。
- 当前角色状态。
- Planner 提供的可选补充上下文、引用原文和 @ 对象。

仅凭 MongoDB 中的群聊记录无法完整还原上述输入。因此，在 Replyer 生成成功后，将实际输入拆为 `system_prompts` 和 `messages` 保存，并记录生成结果，不在审核时重新读取当前提示词或角色状态。

`system_prompts` 按请求拼装顺序保存 `{ key, content }`，`content` 是当次实际使用的渲染结果。当前依次为 `character.persona.<角色 ID>`、`conversation.replyer`、`conversation.replyer.<角色 ID>`；不包含仅用于压缩的提示词。`messages` 去除首条合并的 system message，保留摘要、聊天历史和本轮任务。还原请求时，将数组中的 `content` 用 `\n\n` 拼接为一条 system message，再追加 `messages`，模型实际输入保持不变。

采集异步执行，不阻塞群聊回复。保存生成的正文或控制标记，并将接口实际返回的思考正文独立保存到 `original_reasoning`；接口未返回时不保存该字段，不补写或从正文猜测。生成成功与平台发送成功是不同事实，不能把采集记录直接当成已经发出的群消息。

训练计划使用 Qwen 小模型，并在推理时开启 thinking。当前先采集原始思考内容，不自动作为训练目标；回复被修改后，原思考可能与新回复不一致，需在制作训练集时另行审核。具体模型的消息模板、思考内容标注与导出后续确定。

### 按群开启采集

角色的 `onebot.group_white_list` 支持群号字符串与配置对象混用：

```json
{
  "group_white_list": [
    "821529588",
    {
      "group_id": "1083608109",
      "collect_training_data": true
    }
  ]
}
```

- 字符串仅加入聊天白名单，不开启采集；对象的 `group_id` 必填，`collect_training_data` 可选，只有显式为 `true` 才采集。
- 同一群不能重复声明；配置加载时统一转换成对象，消息入口与会话创建共用该配置。
- 修改后重启生效；采集开关不影响普通聊天归档和记忆整理。测评调用明确关闭采集。
- 开启采集后，每次 Replyer 正常生成非空回复，保存本次实际输入与分段前回复。采集失败只记录错误，不重试、不影响回复；进程退出可能丢失在途采集。
- 示例仅说明配置格式，不代表已经替用户开启这两个群的采集。

## 处理流程

```text
Replyer 实际输入 + 原始生成回复
              ↓
         保存为待审核记录
              ↓
    模型辅助判断质量、给出修改建议
              ↓
      用户审核建议并最终确认
              ↓
      保存为已确认的训练样本
              ↓
      分别导出 SFT / DPO 数据集
```

好回复也需要确认后入库，不能只收集失败案例的改写。数据应覆盖普通接话、玩笑、简短回应等日常交流，避免集中在纠错、拒绝和尴尬场景。

质量判断和改写可由助手或更强的模型辅助完成，用户负责最终确认。模型建议不直接视为已确认的训练样本。接受审核完整上下文所需的 token 开销，不为降低审核成本而丢弃原始输入；具体审核模型与调用流程仍待确定。

## Dashboard 标注页面

新增仅私有部署可见的「回复标注」页面。

- 列表按日期、群聊、审核状态筛选，展示原回复预览。
- 左侧以聊天形式展示生成前的上下文；摘要、角色状态、补充上下文分别折叠，完整模型输入可展开查看。
- 右侧展示只读的原回复和可编辑的目标回复，编辑框默认填入原回复。
- 支持查看模型的审核与改写建议，由用户修改或确认；具体交互方式后续确定。
- 提供「保留原回复」「保存修改」「排除样本」，处理后进入下一条。
- 第一版不做复杂评分维度和修改历史，备注可选。

| 情况 | 操作 | SFT 数据 | DPO 数据 |
| --- | --- | --- | --- |
| 原回复合适 | 保留原回复 | 输入 → 原回复 | 不生成 |
| 应该回复，但内容、语气或人设表现不好 | 修改并保存 | 输入 → 修改后的回复 | 相同输入，修改后为 `chosen`，原回复为 `rejected` |
| 当前无需回复，应该保持沉默 | 将目标回复设为 `[[NO_REPLY]]` 后确认；原本就是该标记则保留 | 输入 → `[[NO_REPLY]]` | 有改写时，沉默标记为 `chosen`，原回复为 `rejected` |
| 输入缺失或补充上下文错误，无法写出合理回复 | 排除并记录原因，后续修正上游 | 不生成 | 不生成 |

本流程约定：人工修改是为了改善不符合预期的回复，修改并保存即表达明确偏好，不额外增加偏好确认或“只是另一种表达”的分类。`rejected` 表示在当前上下文中比修改后的回复差，不要求原回复完全错误；没有实际改动的回复按保留原回复处理。

群友在回复后的反应可以辅助人工判断，但需与模型生成时可见的输入分开展示，不能混入训练输入。

## 数据存储

原始采集与最终训练样本分别存入两张 MongoDB collection。沿用项目环境隔离：生产使用下列名称，开发使用对应的 `_dev` 后缀，不同步到公开部署的数据源。

| 字段 | `replyer_generations` | `replyer_training_samples` |
| --- | --- | --- |
| `_id` | MongoDB 生成的原始记录 ID | MongoDB 独立生成的样本 ID |
| `generation_id` | — | 原始记录 ID，唯一索引 |
| `character_id`、`platform`、`channel_id` | 角色与来源群 | 随样本独立保存 |
| `created_at` / `generated_at` | `created_at`：本次生成完成时间 | `generated_at`：原始生成时间 |
| `confirmed_at` | — | 用户最终确认时间 |
| `expire_at` | 生成完成后 14 天，TTL 索引 | —，长期保留 |
| `system_prompts` | 按顺序保存各 prompt 的 `{ key, content }` | 提示词快照的独立副本 |
| `messages` | 除首条 system message 外的实际输入 | 对应消息的独立副本 |
| `original_reply` | 分段前的原始回复 | 原始回复的独立副本 |
| `original_reasoning` | 可选，接口返回的原始思考正文 | 本阶段不保存，训练时的处理待定 |
| `final_reply` | — | 人工确认的目标回复 |
| `model` | 生成响应中的模型标识 | 随样本保存 |
| `status` | `pending` / `approved` / `excluded` | —，只保存确认后的样本 |

原始表不保存 `input_tokens`。原始输入、思考与回复保持不变，审核只更新状态，不延长过期时间。原始记录无论是否确认都保留 14 天，MongoDB 按 TTL 异步清理。

确认流程待标注功能实现：先按唯一的 `generation_id` 写入或更新训练样本，再将原始记录标记为 `approved`；重复确认更新同一样本。样本 `_id` 不使用原始记录的 ID。两表短期内有意重复保存完整输入，避免原始记录过期后训练样本失效。

`generation_id` 仅用于追溯，原始记录过期不级联删除训练样本。最终回复与原回复是否不同，决定能否导出 DPO 偏好对，不重复存储两套 SFT / DPO 样本。审核备注不参与训练。

本阶段在首次采集时创建两张表及索引，只写原始记录；确认写入、标注与导出尚未实现。原始表按角色、状态、群与生成时间建立查询索引，训练表按 `generation_id` 唯一索引和角色、生成时间索引建立。

数据库字段统一使用下划线命名，JS 函数与变量保持驼峰；`messages` 内保留 SDK 原始消息结构。已有驼峰字段记录需在部署前迁移，并移除旧字段索引、建立新字段索引，特别是唯一索引与 TTL 索引；应用不自动迁移或兼容旧结构。

`system_prompts` 拆分也是存储结构变更：旧记录中的合并提示词不会自动按 key 拆分，不能用当前提示词替代历史快照；本次不迁移已有记录。

## 数据导出

SFT 导出所有已确认样本，逻辑结构为：

```text
由 system_prompts + messages 还原的完整 Replyer 输入
+
人工确认的回复，作为最后一条 assistant 消息
```

DPO 只导出已确认且实际修改了回复的样本，逻辑结构为：

```text
共同输入：由 system_prompts + messages 还原的完整 Replyer 输入
chosen：人工修改并确认的回复
rejected：原始生成回复
```

两个候选必须对应同一份完整输入。第一版只修改目标回复，不修改输入，不能把不同上下文下的回复配成一对。

不把审核备注、原来的错误回复或生成后才出现的群聊信息追加到训练输入。原始错误回复仅在 DPO 中作为 `rejected` 导出，不作为 SFT 的目标回复。

训练平台的具体文件格式等选定模型和训练方式后再适配。固定评测集的划分后续单独讨论。

## 历史记录与后续讨论

已有历史聊天可以用于人工构造样本，但缺少当时完整的请求快照，不能视作原始请求的精确还原。建议第一版先采集新的真实生成记录，历史数据导入后续处理。

以下问题尚未确定，不作为本轮实施要求：

- 完整输入快照的实际存储体积；先按两张表独立保存完整输入，原始记录保留 14 天。
- 模型辅助审核使用哪个模型、如何调用，以及用户最终确认的具体交互。
- 如何辅助筛选值得审核的样本，避免人工浏览大量重复场景。
- 选定微调模型与训练资源后，如何处理超过训练长度限制的样本；不能直接截断后使用原目标回复。
- 训练集与固定评测集如何划分，避免同一段聊天同时出现在两者中。
