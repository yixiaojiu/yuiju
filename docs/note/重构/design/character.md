## 角色模块

## 角色的业务状态

| 类别           | 包含内容                                 | 例子                                       |
| -------------- | ---------------------------------------- | ------------------------------------------ |
| 当前情绪与想法 | 此刻的感受、近期在意的事情               | 对今晚直播有些期待，又有点紧张             |
| 计划与日程     | 未来安排、推进情况、下次关注时间         | 晚上直播，提前回家准备                     |
| 记忆与认知     | 已有生活背景、新经历、对人物和往事的认识 | 记得上次直播聊过什么，对某位群友有什么印象 |

## 情绪

### 情绪维度

第一版采用三个维度，程序根据维度数值生成供 LLM 理解的情绪描述：

| 维度 | 低值 | 高值 | 含义 |
| --- | --- | --- | --- |
| 愉悦度 | 不愉快、低落 | 愉快、满足 | 感受的正负倾向 |
| 激活度 | 平静、低激活 | 活跃、激动 | 情绪的激活程度，不等同于身体体力，也不单独表示情绪的正负 |
| 掌控感 | 受制、无力影响处境 | 自主、能影响处境 | 此刻感到自主还是受制，不是任务成功率、长期自信或控制他人的欲望 |

维度描述总体情绪，具体事情与感受保留自然语言，与维度描述一起提供给 LLM。不同事情上的感受可以并存，不将某件事上的无力感解释为角色在所有处境中都无能为力。

### 情绪数值转文本

三个维度统一使用 `0～100`。程序分别按区间选择描述，再按“愉悦度、激活度、掌控感”的固定顺序组合成纯文本，不额外调用 LLM。第一版使用以下分档草案，区间是产品表达规则，不是心理学上的精确分界：

| 数值区间 | 愉悦度描述 | 激活度描述 | 掌控感描述 |
| --- | --- | --- | --- |
| `[0, 20)` | 整体感受很不愉快 | 情绪激活程度很低 | 明显感到受制，难以影响当前处境 |
| `[20, 40)` | 整体感受偏不愉快 | 情绪较平静 | 有些受制，觉得能影响处境的空间有限 |
| `[40, 60)` | 愉快与不愉快的倾向均不突出 | 情绪激活程度适中 | 自主与受制的倾向均不突出 |
| `[60, 80)` | 整体感受比较愉快 | 情绪较活跃 | 比较有自主感，觉得能够影响当前处境 |
| `[80, 100]` | 整体感受非常愉快 | 情绪高度激活，较为激动 | 自主感很强，觉得能主动影响当前处境 |

例如，愉悦度为 75、激活度为 85、掌控感为 30 时，生成：

```text
当前情绪：整体感受比较愉快；情绪高度激活，较为激动；有些受制，觉得能影响处境的空间有限。
```

生成规则：

- 三个维度独立描述，用分号连接，不维护所有维度组合的专用文案，也不额外推断因果关系。
- 文案不绑定直播、工作或社交等具体场景，不直接推导“害羞”“愤怒”“害怕”等具体情绪标签；原因与对象由自然语言感受补充。
- 低激活不等于悲伤，高激活不等于开心；低掌控不等于能力不足，高掌控也不保证事情会成功。
- 中间档表示该维度没有明显方向，不代表没有情绪，也不否定同时存在的复杂感受。
- 描述用于提供主观状态背景，不直接生成行动指令、人格判断或世界事实。
- 第一版采用直接分档；若实际出现边界附近措辞频繁切换，再评估档位切换缓冲，不预先增加平滑机制。

### 更新方式与策略

主 agent 使用自然语言描述对某件事的感受，不直接填写或修改情绪数值。直播等场景由当前负责决策的 loop 提交感受，情绪 sub-agent 只负责情绪处理，不掌握角色行动决策权。

```text
主 agent / 场景 loop 提交自然语言感受
  → 情绪 sub-agent 结合当前数值、已有感受与本次描述判断是否需要更新
  → 通过更新策略后，由 sub-agent 结合程序更新数值
  → 程序生成情绪文本，供后续思考和交流使用
```

更新策略统一放在情绪 sub-agent 的处理流程中拦截，不要求主 agent 自行控制更新频率。该流程可以判断是否为重复表达、是否存在实质变化，以及是否需要合并频繁提交；允许接收感受后不修改数值，不能每次提交都固定增加或减少某个维度。

需要精确计时、去重或串行处理的规则由该流程中的程序执行，不依赖模型自行计数。具体频率、合批窗口和变化阈值暂不确定。

情绪可以因事件立即变化，不强制缓慢过渡。低延迟场景中的情绪处理不阻塞当前回复，当前感受可以直接影响本次表达，系统数值更新后用于后续调用。

## 计划与日程

计划表达角色未来的打算，有明确时间安排时同时是一项日程，使用同一种模型，不另建自动执行任务系统。由 `character-runtime` 管理，主 loop 与场景 loop 共享；当前掌握行动决策权的 loop 负责创建和修改，聊天模块可以查询、提出安排请求。

### 计划内容

| 内容 | 用途 |
| --- | --- |
| 计划 ID | 程序生成，用于后续修改和关联事件 |
| 内容 | 想做什么，以及相关背景 |
| 计划时间 | 事情安排在什么时候，可以为空 |
| 下次关注时间 | 何时产生事件，让大脑考虑这件事，可以为空 |
| 状态 | 待进行、进行中、已完成、已取消 |
| 进展说明 | 已做到哪里，以及调整安排的原因 |

计划时间和下次关注时间分开。例如 20:00 直播，可以安排 19:30 开始关注并准备。推迟关注时间不一定意味着改变约定的直播时间。

没有明确时间的打算也可以保存，例如“最近想去海边走走”。它不产生到点事件，大脑在考虑下一步生活安排时查看未完成计划。

### 运转流程

```text
大脑确定今晚直播
  → 保存计划：20:00 直播，19:30 关注
  → 19:30 到达，程序产生计划关注事件
  → 大脑结合当前情况决定回家，更新准备进展
  → 收到到家事件，再决定下一步；需要等待时设置下次关注时间
  → 直播开始，更新为进行中
  → 直播结束，根据实际结果更新为已完成
```

- 到点只触发关注，不自动执行，也不自动判定失败。大脑可以根据现状推进、调整或取消计划。
- 已触发的关注时间被消费，避免每次检查都重复发送事件；需要再次关注时明确设置新时间。
- 计划变更时同步更新对应的时间触发，完成或取消后撤销后续触发。
- 计划描述整体意图与进展，世界管理具体活动。例如准备直播可以涉及回家、等待和开播，不预先固化为必须逐项执行的步骤。
- 完成状态应依据实际结果，不能把生成的打算当成已经执行。

### 工具能力与第一版范围

- 查询计划：查看未完成计划或某一项详情。
- 创建计划：提交内容，以及需要的时间安排。
- 修改计划：按 ID 修改时间、进展或状态。取消通过修改状态表达，不删除已经发生过的安排。

第一版支持单次计划、时间触发、进展更新和结束。暂不设计重复日程、子任务或计划依赖关系。

## 记忆与认知

沿用旧系统“经历整理、长期保存、按需回忆”的大体思路，以人物画像、经历记忆和自我认知组织内容。三类记忆统一每天整理一次，原始经历材料仍及时记录，整理在后台进行，不阻塞当前思考与聊天。具体执行时刻、存储格式和更新策略继续细化。

记忆由 `character-runtime` 管理，按角色隔离，同一角色的主 loop、聊天和场景 loop 共享。角色一开始就在世界中生活，需要有符合背景的已有记忆与认识，不从空白开始积累。核心人设与世界观保持稳定，不通过日常记忆更新自动改写。

| 内容 | 表达什么 | 使用方式 |
| --- | --- | --- |
| 自我认知 | 我最近过得怎么样，对近期生活有什么认识 | 作为大脑的常驻上下文 |
| 经历记忆 | 过去发生过什么，当时有什么感受 | 根据当前需要检索、回忆 |
| 人物画像 | 我知道这个人的哪些事情，我如何看待对方及彼此的关系 | 随当前交往对象加载，也可以主动查询 |

### 自我认知

自我认知是新增内容，用短篇自然语言表达角色对近期生活的整体认识，可以跨越多次经历，不等同于当前情绪，也不用于总结或改变核心性格。

例如：

> 最近在咖啡店打工已经比较熟悉了，但忙起来还是会有些紧张。下班后常常只想回家待着，之前很喜欢的散步最近少了些。和小雨聊天越来越自在，不过上次聊到直播时，我还有一点犹豫。

更新流程草案：

```text
旧自我认知 + 新增经历 + 角色已有的感受与思考
  → 判断近期生活认识是否发生变化
  → 需要更新时生成完整正文，保存正文与更新时间
```

- 每天整理一次，具体执行时刻待定；没有实质变化时不强制改写正文。
- 只整理已有经历和认识，不额外编造动机、感受或人生感悟。
- 计划的执行状态仍由计划模块维护，情绪数值仍由情绪模块维护，不以自我认知正文代替这些状态。
- 创建角色时提供符合既有生活背景的初始自我认知。
- 旧系统的“核心记忆”保存少量珍贵经历，并非这里的自我认知；这类经历如何保留，后续结合经历记忆细化。

### 经历记忆

经历记忆是角色大脑对过往生活的记忆，角色通过它回顾往事。正文记录事情、当时的感受及必要背景，不要求写成完整文章。

例如：

> 周五傍晚在咖啡店打工，客人比平常多。出餐时漏了一杯饮料，发现后补上了。当时很慌，收工后又觉得自己至少把事情处理好了。

沿用旧系统按时间查询和语义检索的思路。近期记忆每天批量整理一次，存储和检索能定位到相对完整的一件事，具体切分粒度待定。每日整理同时检查并更新需要的周、月、年概括；随着时间推移，角色只能回忆更抽象的记忆，不能一直查询全部细节。

- 程序维护时间、涉及人物、地点、来源经历等已有信息，模型负责整理记忆正文，不重新猜测已有元信息。
- 保留事情经过与当时的主观感受，区分亲身经历、线上交流及他人转述，不能将转述直接写成亲历事实。
- 记忆整理与 agent loop 的上下文压缩是不同流程，压缩摘要不自动成为新的经历依据。

#### 随时间遗忘

按经历距今的时间限制可回忆的精细程度，逐步从具体经历转为较长时期的概括：

| 经历发生距今的时间 | 可回忆的最细粒度 |
| --- | --- |
| 近 7 天（含第 7 天） | 具体经历，包括事情经过与当时的感受 |
| 超过 7 天，至 30 天（含） | 周记忆，概括一周的主要经历与感受 |
| 超过 30 天，至 180 天（含） | 月记忆，概括一个月的生活状况与重要变化 |
| 超过 180 天 | 年记忆，保留更长期的生活轮廓 |

- 周、月、年记忆由对应时期内较细粒度的记忆整理形成，细节逐步丢失，不要求能够还原原始经历。
- 时间阈值由程序控制。遗忘依据经历发生时间，不因重新整理或检索而重新计时。
- 年记忆按经历所属年份归并，不需要等满一年才生成；同一年的概括随着较细记忆到期继续补充。
- 时间查询与语义检索遵守同一粒度限制；超过期限后，不能通过更精确的查询、来源关联或其他工具重新取回已不可回忆的细节。
- 较细记忆退出可回忆范围前，应完成对应的较粗记忆整理。底层细节是否物理删除或仅退出角色可访问范围，后续确定。
- 抽象记忆中没有保留的细节应视为已经记不清，不能让模型补写成确定的往事。

回忆流程：

```text
大脑或聊天提出当前回忆目标
  → 检索 agent 按时间或语义查询，程序限制各时期可访问的记忆粒度
  → 返回仍可回忆的具体经历或周、月、年概括，必要时查询人物画像
  → 当前 loop 结合此刻状态理解这些往事
```

同一件事在不同心情下可以有不同解读。例如当时觉得一次工作失误很丢脸，后来回想时觉得自己处理得还不错。新的解读不直接改写过去发生的事情或当时的感受。

### 人物画像

沿用旧系统为每个人维护画像的思路，但调整存储内容和格式。画像表达“我对这个人的认识”，不直接沿用旧系统的七个固定栏目。

认知逐条保存，每条包含日期和自然语言内容，暂按两类组织：

| 内容 | 示例 |
| --- | --- |
| 我知道的事 | 她说自己最近在准备考试，平时喜欢画画，不喜欢被叫某个外号 |
| 我对她的认识与关系感受 | 聊天经常互相开玩笑；她谈到考试时比较认真，我会收敛一些。最近觉得和她熟悉了不少 |

- 区分对方提供的信息与角色自己的印象，不能把“我觉得她很冷淡”写成客观的人格定论。
- 程序维护稳定的人物标识、称呼和更新时间，模型整理逐条认知，不要求模型生成复杂的结构化档案。
- 使用稳定人物标识定位画像，不再以昵称作为唯一标识。同一角色在多个群认识的同一个人共享画像。
- 具体互动经过保存在经历记忆里，画像保存这些互动形成的认识，必要时关联相应记忆，不只反复覆盖“最近一次互动”。

#### 平台身份与跨平台关联

平台身份使用“平台来源 + 平台用户 ID”唯一定位，昵称只用于展示。各平台画像分别保存在 `memory/people/<platform>/<platformUserId>.json`，跨平台身份关联保存在 `memory/people/links.json`。

```text
同一人的关联身份
  ├─ QQ：用户 123 → qq/123.json
  └─ Discord：用户 456 → discord/456.json
```

- 用户在 dashboard 中手动关联属于同一个人的不同平台身份，不根据相同昵称或模型猜测自动关联。
- 关联后，加载和更新画像时结合各关联身份的认知，将其视为同一个人；回忆时可以检索各关联身份的相关经历。不同角色仍各自维护对这个人的认识。
- 各平台画像不合并成一个文件，每条认知仍保留在其来源平台的画像中，保留日期和来源，不因关联操作刷新日期。
- 记忆保留原始平台和会话来源；身份关联不改变原有的交流范围，不意味着可以跨群披露聊天内容，也不绕过经历记忆的遗忘规则。
- 解除关联后，不再联合加载这些身份的画像；跨平台经历共同形成的认知如何处理，后续另行设计。

#### 认知日期

每条认知记录支持它的最近一次经历日期，用于表达认识的新旧程度，并作为遗忘的依据。例如：

```text
我知道的事：
- 2026-09-20：她说最近在准备考试。
- 2026-09-25：她平时喜欢画画，今天又聊起了正在画的作品。

我对她的认识与关系感受：
- 2026-09-25：最近聊天越来越自在，经常互相开玩笑。
```

日期来自实际互动或其他认知依据，不使用整理任务的执行日期。新的经历再次支持某条认知时可以更新日期；仅仅读取、改写或合并旧内容不能刷新日期，也不能因为与这个人有了新互动就刷新全部认知。

#### 认知遗忘

人物画像需要主动整理和遗忘，不能只追加新认知，也不能把所有历史版本留在画像正文中。

- 新认识替代已经过时的认识；相同或相近的认知合并，具体互动细节交给经历记忆保存。
- 长期没有新依据的认知逐步遗忘，短期近况与长期偏好、关系认识应区分处理，不直接套用经历记忆的周、月、年分层。
- 每个人物画像需要有容量上限，避免持续互动让认知无限增长。达到上限时重新评估已有内容，删除过时、重复或相对不重要的认知。
- 人物画像每天整理一次，包含更新与遗忘检查；长期不再互动的画像也需要清理，不能只在新互动时检查。

更新时结合已有画像与新增互动，判断哪些认识需要新增、保留、调整或遗忘。具体遗忘期限、容量上限、每日执行时刻与文件格式后续确定。
