## 项目配置

- 配置保存到 JSON，应用启动时读取，修改后重启对应应用生效。各种配置可以直接在 dashboard 中编辑。
- 在项目根目录有一个 data/ 目录，目录不存在就自动创建，用来存配置文件、memory 等数据。

```
data/
  config/config.json
  characters/
    <characterId>/
      memory/
        self-cognition.json
        people/
          links.json
          <platform>/
            <platformUserId>.json
```

- `self-cognition.json` 保存角色当前的自我认知正文与更新时间。
- `people/<platform>/<platformUserId>.json` 保存该平台身份的人物画像，包括称呼、逐条认知、日期和来源。同一平台身份在不同群聊中共用画像。
- `people/links.json` 保存用户在 dashboard 中手动设置的跨平台身份关联。各平台画像分别存储，加载和更新时结合关联身份的认知，每条认知仍保留在其来源平台的画像中。
- 经历记忆及周、月、年概括保存到数据库，不在此目录保存正文。

## Agent Loop 上下文压缩

上下文由固定的人设与场景规则、历史摘要、近期原始记录组成。压缩只整理较旧的历史，不改写固定设定，也不删除原始历史记录；上下文摘要不替代长期记忆、实时状态或计划。

### 低延迟场景：提前异步压缩

聊天、直播等场景将压缩移出正常回复路径。在上下文达到预设预算时，提前启动后台压缩，为压缩期间新增的内容预留空间；具体预算后续结合模型和场景确定。

后台任务固定本次压缩范围，将旧摘要与一段较旧的完整历史整理为新摘要。任务执行期间，loop 继续使用原上下文处理新事件；压缩完成后，在下一次模型调用前替换摘要及其覆盖的旧记录，保留覆盖范围之后的全部记录。

```text
当前上下文：旧摘要 + 事件 1～100

后台开始压缩：旧摘要 + 事件 1～70
直播继续使用原上下文，处理 71～100，以及新到的 101、102……

后台完成后：
下一步上下文 = 新摘要（覆盖到 70）+ 71～最新事件
```

示例中的编号表示历史顺序，实际压缩范围包含对应的事件、模型回复、工具调用与结果。边界必须落在完整交互结束处，不能拆开工具调用与对应结果。

- 每个 loop 的上下文分别管理，同时最多进行一个压缩任务。
- 明确记录摘要覆盖的位置，不覆盖压缩期间新增的内容，也不重复保留已被替换的旧记录。
- 已发出的模型调用继续使用原上下文，替换只影响后续调用。
- 压缩成功后才替换；失败时保留原上下文。若尚未完成压缩就达到上下文硬上限，暂停后续生成，待压缩成功且上下文满足预算后再继续，不静默丢弃记录。
- 后台压缩的并发安排不能挤占低延迟回复所需的调用额度。

#### 直播 loop 的摘要内容

直播摘要用于接续交流与节目进展，使用独立的压缩提示词。模型只输出纯文本，不生成 Markdown 标题、JSON 或外层标签；上下文位置、覆盖时间与记录位置由程序负责组织和标注。

重点保留：

- 当前话题、已经聊到哪里，以及直播环节的进展。
- 角色已经说过的重要内容、对观众作出的表达和安排，必要时保留少量原话以延续语气。
- 观众的重要回应及对应人物、尚未回答的问题和没有接完的话题。
- 影响后续互动的实际工具结果，区分打算做、已经开始和已经完成。

省略无关弹幕、重复互动、已结束且不影响后续的小话题，以及每次回复背后的冗长规划过程。更新摘要时清理已解决的事项，不编造事实、情绪或动机。摘要描述的是截至覆盖范围结束时的情况，后续原始记录和最新查询结果用于判断当前状态。

纯文本输出示例：

```text
刚讲完第一次做饭放错调料的故事，用户 A 说自己也犯过同样的错，她笑着回应“原来不止我一个”。用户 B 接着问后来那锅饭怎么处理，截至这段记录结束还没回答。她之前说过聊完这段再唱歌，目前仍在聊天环节。
```

### 主大脑：按需同步压缩

主大脑允许等待压缩完成。在下一次模型调用前检查上下文预算，接近预算时，将旧摘要与较旧的完整交互同步整理为新摘要，保留近期原始记录，再继续决策。

```text
完整步骤结束 → 检查上下文预算 → 需要时同步压缩 → 替换旧摘要与覆盖记录 → 继续调用模型
```

主大脑具体压缩哪些内容、采用什么摘要组织方式和提示词暂不确定，后续参考其他 agent 的做法，再结合角色持续生活的特点设计。上述同步压缩调度策略保持不变。不在工具执行中途压缩，也不将摘要中的旧状态当成当前状态。

压缩期间到来的新事件继续收集，沿用当前轮结束后下一轮一起处理的规则，不混入正在压缩的历史范围。压缩失败时保留原记录，不带着超出预算的上下文继续调用模型。

两类策略都按 token 预算判断，而不是固定消息条数；预算需要计入固定内容、工具定义、历史和本次输入，为输出留出空间，并兼顾已配置的备用模型。
