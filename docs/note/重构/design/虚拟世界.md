# 虚拟世界

## 实现范围

第一版完整实现旧虚拟世界的地点和活动，旧代码作为内容与规则的参考，新架构重新设计

地点之间已有的移动路线，以及支撑活动的商品、食材和资源也纳入第一版。需要调整的业务规则单独讨论，不因重写架构而直接改变。

## 核心设计

以下内容逐项确定，暂不展开具体接口、字段和实现细节。

### 1. 世界如何运转

沿用旧应用的现实时间与恢复规则，世界引擎采用固定 tick：

- 世界时间跟随现实时间，不加速。
- tick 串行执行，上一轮完成后等待 1 秒再执行下一轮，不重叠。间隔先作为代码常量，不开放 Dashboard 配置。
- 每次 tick 检查到期活动、天气、场景和资源，只处理实际需要变化的内容，各系统仍按自身规则更新。
- 按真实时间判断是否到期，不通过累计 tick 次数计时。
- HTTP 行动请求即时处理，不等待下一次 tick；请求与 tick 对世界状态的修改需要统一协调。
- 没有变化时，不写历史、不推送事件、不调用 LLM。
- 启动时，从上次推进时间按各系统规则更新到当前时间，停机不冻结世界时间。
- 未完成活动按原定结束时间恢复：未到时间继续等待，已经到期则执行完成结算；不补造停机期间角色的新决策和行动。

新系统调整大脑与世界的执行边界及检查频率，保留原有时间与业务变化规则。

### 2. 世界如何建模

确定地点、角色、物品和活动之间的关系，以及世界与大脑各自管理哪些状态。第一版接入悠酱，模型需要能够容纳多个角色。

#### 地点建模

- **层级关系使用树结构。** 表达地点的包含关系，例如小镇包含住宅区，住宅区包含家，家包含客厅、厨房和卧室；不固定为两层。
- **同一层使用图结构。** 地点作为节点，通行路线作为边，描述哪些地点直接相通，以及通行方式、耗时和费用。
- 层级包含不代表直接相通，跨层进出通过明确的入口衔接，具体入口规则后续确定。
- 地图需要提供一致的空间布局与相对方位。图的连通关系本身不能表达东西南北，方位与路线信息应依据地图定义生成。
- 角色记录当前所在的具体地点，所属区域由层级关系得到。

#### 归属世界的状态

| 类别           | 主要内容                                                         |
| -------------- | ---------------------------------------------------------------- |
| 世界环境       | 当前天气、上次推进时间、环境更新安排                             |
| 地点状态       | 可用资源及数量、动态开放情况、正在发生的场景事件                 |
| 角色身体       | 体力、饱腹等身体状态                                             |
| 角色位置       | 当前地点；移动中的起点、终点和进度，与移动活动保持一致           |
| 角色资产与设备 | 金币、背包物品及数量、手机电量                                   |
| 进行中的活动   | 所属角色、行动及参数、开始与预计结束时间、实际进展、结算所需信息 |

角色相关状态按角色 ID 分别管理。正在打工、睡觉或移动等情况由活动记录表达，不另存独立的布尔开关。可由已有数据得到的信息按需计算，例如地点内有哪些角色、活动剩余时间；不重复保存同一事实。

地点层级、通行路线、物品定义和行动条件属于世界内容与规则，不属于运行状态。世界事实记录与当前状态分开保存。角色的人设、记忆、计划和 loop 控制权不归世界管理；心情的归属尚未确定，暂不纳入上述清单。

### 3. 行动如何执行

确定行动从开始到结束的过程、状态结算方式，以及中断和并行规则。重点走通打工、移动、玩手机和直播这些有持续时间的活动。

#### 行动如何呈现给大脑

区分“知道有这个行动”和“现在可以执行”。不再仅向大脑提供通过前置条件检查的行动列表，避免角色因为暂时不满足条件，就不知道某个地点能做什么、如何准备。

1. **了解活动。** 查询角色已知的地点时，可以了解那里提供哪些活动，以及活动的条件、耗时和结果规则。展示活动不代表允许立即执行。
2. **检查当前条件。** 需要判断可行性时，结合角色与世界当前状态，返回是否可执行及未满足的条件，而不只是 `true/false`。
3. **决定如何准备。** 大脑根据这些信息决定先休息、移动或进行其他准备，世界不替角色规划。
4. **请求执行。** 大脑提交行动请求，世界根据最新状态重新检查，满足条件才开始行动。

例如，悠酱在家且体力不足时，仍能查询到咖啡店提供打工活动，了解到打工需要到店、处于工作时段并满足体力要求。当前检查会说明“尚未到店、体力不足”，大脑据此决定先休息再前往。到店后请求打工，世界再次检查条件。

活动规则说明与实际执行检查来自同一份条件定义，避免维护两套不一致的规则。

所有信息仍受角色视角限制。“当前不满足”与“当前不知道”需要区分：角色可以知道咖啡店提供工作，但若某项动态信息必须到店才能获得，远程查询不能直接透露，也不能将未知当成条件已满足。

#### 行动参数与执行流程

世界为每个行动定义参数 schema，但不为每个行动分别暴露 function tool，也不动态修改执行工具的 schema。大脑按需查询某个行动的完整信息，避免每次调用都携带所有行动的参数定义。

1. **查询行动。** 返回行动说明、执行条件、参数 schema，以及角色可知的选项，例如商品 ID、名称和价格。
2. **选择参数。** 大脑按照 schema 选择参数，构造 JSON 字符串；世界不再调用 LLM 替角色完成选择。
3. **提交执行。** 调用 `execute_action`，传入 `actionId` 和字符串类型的 `payload`。没有执行参数的行动统一传入 `"{}"`。
4. **解析与检查。** 世界解析 `payload`，使用该行动的参数 schema 校验结构，再根据最新状态检查业务条件，全部通过后才执行。

购买示例：

```json
{
  "actionId": "买商品",
  "payload": "{\"items\":[{\"itemId\":\"egg\",\"quantity\":2}]}"
}
```

查询返回的 schema 与执行校验使用同一份行动定义，不接受模型提交或修改 schema。参数校验与业务检查分开：数量必须为正整数属于参数校验，是否在店内、余额是否足够属于业务检查。

JSON 解析或参数校验失败时返回具体错误，由大脑修正；不自动补值或调用其他模型修复。工具层只约束 `payload` 是字符串，其内部是否符合行动 schema 由世界校验。

### 4. 世界如何被角色感知

确定世界变化如何转成角色可感知的信息与事件，以及直播等场景如何收窄输入。通信沿用 HTTP 查询与行动请求、WebSocket 事件推送。

#### 提供给角色的 function tool

先提供两个工具，查询工具的具体参数与返回字段在实现设计时确定，执行工具固定接收 `actionId` 和 JSON 字符串 `payload`：

| 工具             | 职责                                                               | 返回内容                                                                                                                        |
| ---------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `inspect_world`  | 查询当前环境、已知地点或两个已知地点的关系，也可查询指定行动的信息 | 地点 ID 与名称、所属层级、地图概况、相对方位、通行路线与耗时；查询指定行动时提供说明、条件、参数 schema、可知选项及当前执行情况 |
| `execute_action` | 通过 `actionId` 和 `payload` 提交选定行动及参数，移动也属于行动    | 参数校验与最新业务条件检查后的处理结果；持续活动返回已开始及预计结束时间，完成后另发事件；不能执行时说明原因                    |

行动由角色大脑选择，不另设“选择行为”工具。查询结果使用稳定 ID 支持后续调用，同时提供自然语言描述帮助角色理解位置和活动。

地点信息区分熟悉区域的地图知识与当前位置的实时感知。角色可以知道远处地点的方位和路线，但不能因此查询到无法感知的实时情况。当前位置的基本感知可随到达等事件提供，信息不足时再调用查询工具。

## Action 定义

| 内容        | 职责                                                         |
| ----------- | ------------------------------------------------------------ |
| 名称、说明  | 让角色识别和理解行动                                         |
| 参数 schema | 定义大脑需要选择什么；无参数行动使用空对象                   |
| 适用范围    | 这个行动属于哪些地点，或是通用行动                           |
| 选项查询    | 按角色和地点提供商品、食材等动态选项，没有选择项的行动不需要 |
| 条件        | 描述执行要求，并检查当前是否满足                             |
| 开始处理    | 确定持续时间，执行立即发生的状态变化                         |
| 完成处理    | 活动结束时结算，并产生实际结果                               |
| 持续时间    |                                                              |
