# 扩展包设计

本文记录目前讨论的设计方向，供后续继续调整，尚未实现。

## 1. 目标与边界

将具体 sub agent、互动等场景能力放到独立扩展包中，不继续堆进 `character-runtime`。

- `character-runtime` 仍是角色的运行宿主，每个进程运行一个指定角色，管理角色状态、任务投递、事件路由与行动决策权。
- 扩展包维护具体能力，可以同时提供 agent、前端组件、HTTP 接口和通信协议；不要求每个扩展都包含所有入口。
- Dashboard 承载扩展页面和 Hono API，不创建另一份角色 agent，也不接管角色状态。
- 扩展按包名显式登记，优先从 data/extensions 查找，其次解析项目根目录的 pnpm 依赖；宿主运行前及 Dashboard 构建前生成导入表。仓库内开发可使用 workspace 依赖；暂不做运行时安装、自动发现、热加载或独立进程通信。
- 同一扩展按角色创建独立运行实例，不在包级全局变量中共享角色状态。

## 2. 两类 agent

| | 任务型 sub agent | 接管注意力的场景 agent |
| --- | --- | --- |
| 职责 | 完成一次委托并返回结果 | 持续参与某个场景 |
| 主 agent | 同步调用时等待；异步调用后继续运行 | 暂停决策，让出控制权 |
| 输入 | 任务参数、必要上下文 | 场景事件及允许接收的角色事件 |
| 输出 | 工具返回值或完成事件 | 持续调用工具，退出时交还控制权 |
| 生命周期 | 任务开始到完成 | 进入场景到退出 |
| 世界行动权 | 不因被调用而获得 | 随控制权交接获得 |

### 任务型 sub agent

任务型 sub agent 在 `agent.ts` 导出的配置对象中通过 `agents[].type: "task"` 声明。同步和异步调用同一个任务入口，由宿主决定如何等待、交付结果，不在扩展声明中写死调用方式。

```text
同步：主 agent 调用工具 → sub agent 执行 → 工具返回结果

异步：主 agent 调用工具 → 返回任务 ID，主 agent 继续运行
                         ↓
                    sub agent 后台执行
                         ↓
                    完成事件进入调用方待处理事件集合
```

- “待处理事件集合”就是调用方尚未处理的事件，调用方下一轮统一处理，不是另建一套消息系统。
- 扩展只负责执行任务、返回结果；同步工具返回和异步结果事件投递由宿主处理，扩展不自行维护事件队列。
- 异步结果关联原任务和调用方，不按完成时的当前控制者随意投递。
- 如果主 agent 发起任务后进入互动场景，结果留给主 agent 恢复控制权后处理，不强行唤醒它参与决策。
- 不自动复制主 agent 的全部上下文。扩展通过明确输入及宿主提供的查询能力获取所需信息。

### 场景 agent

交接的是角色的行动决策权，不只是更换模型或提示词。

```text
主 agent 决定进入场景
  → 检查进入条件、准备场景
  → 当前执行到安全交接点
  → runtime 将控制权交给场景 agent
  → 场景 agent 持续处理事件、调用工具
  → 退出场景，提交过程摘要与结束原因
  → runtime 交还控制权，唤醒主 agent
```

- 同一时刻只有一个 agent 掌握行动决策权。交接后，旧 agent 不能继续提交世界行动，限制由程序执行，不仅依靠提示词。
- 主 agent 暂停期间，世界继续运行。紧急世界事件交给当前场景 agent，普通事件按场景收窄。
- 一轮处理期间到达的新事件先收集，下一轮再处理，不插入正在执行的轮次。
- QQ 聊天保持独立，不参与行动决策权竞争；是否继续参与聊天，由当前活动与场景规则决定。
- 场景退出是明确的生命周期操作。`vtuber_act` 等普通工具按需调用，不代表一轮或整个场景结束。
- 控制权协调属于 runtime，现有 `agent-loop/control.ts` 可承担这一职责，不放进某个场景扩展。

## 3. 宿主与扩展的职责

| 角色 | 负责内容 |
| --- | --- |
| character-runtime | 创建和销毁角色的扩展实例、注册能力入口、调用任务、投递结果、控制权交接、事件路由 |
| 扩展包 | 专属 loop、工具、模型选择、压缩策略、提示词、外部服务接入与局部运行状态 |
| Dashboard | 页面挂载、Hono 路由挂载、访问权限及页面所需的连接信息 |
| shared | 实际共用的接口类型、技术能力、公共 UI 和提示词模板能力 |

扩展通过宿主提供的接口访问记忆、情绪、计划和世界交互等业务能力，不反向导入 `apps/character-runtime/src/...` 或 Dashboard 内部文件，也不直接修改角色的 Redis 数据。

扩展自有数据由扩展自己的存储模块管理，可以直接从 shared 获取 Redis、MongoDB 连接。连接能力共用，存储实现归所属模块，角色与世界业务数据仍通过宿主接口访问。

宿主能力显式传入：agent 获得角色能力，API 获得必要的服务能力，页面获得角色、会话、接口地址和资源 URL。

扩展专属提示词跟随扩展包维护，由宿主接入模板系统；公共人设按角色提供。不让 shared 的提示词清单反向导入各扩展包。

## 4. 包结构与接入

### 包命名与目录

扩展包名统一以 `yuiju-` 开头，例如 `yuiju-interaction`、`yuiju-reflection`。包名同时作为扩展标识，不再额外定义一个近似 ID。

以仓库内开发的互动扩展为例；外部安装包采用相同的入口约定：

```text
data/config/config.json        # 顶层登记扩展包，角色配置决定是否启用

apps/character-runtime/src/
  agent-loop/control.ts
  extensions/                  # 扩展装配、调用与生命周期管理

packages/yuiju-interaction/
  package.json                 # 不设置 exports，允许直接导入包内文件
  agent.ts                     # 可选，导出 agent 配置对象
  api.ts                       # 可选，导出 API 配置对象
  web.ts                       # 可选，导出页面配置对象
  src/
    runtime/
      agent.ts                 # 场景 agent、工具、场景状态
    web/
      interaction-page.tsx     # 互动页面
      live2d-stage.tsx         # Live2D 渲染与控制
    api/                       # 页面所需的 Hono 接口
    protocol.ts                # 请求、响应与事件契约

packages/shared/src/
  agent/                       # 宿主与扩展共同使用的接口类型
  ui/                          # 公共 UI 组件和主题
```

依赖方向：

```text
character-runtime → 扩展的 agent.ts 配置入口
Dashboard         → 扩展的 web.ts、api.ts 配置入口
两端               → 扩展的 protocol
扩展               → shared 的具体公共能力
```

- 使用能够定位具体声明文件的导入路径，不通过统一根入口混合导出前后端代码。
- `web` 不得间接加载数据库、模型密钥或其他服务端实现；Live2D 渲染代码仅在浏览器加载。
- Dashboard 通过统一页面入口匹配扩展声明的组件，Hono 根据声明挂载扩展路由。
- 扩展不自行监听端口。实时连接能力由 runtime 的扩展宿主提供，不由每个扩展各建一套服务。

### 扩展声明与项目配置

| 位置 | 职责 |
| --- | --- |
| 扩展包的 `agent.ts`、`api.ts`、`web.ts` | 分别导出配置对象，直接引用 agent 实现、Hono 实例和 React 组件 |
| `data/config/config.json` 的顶层 `extensions` | 显式登记当前部署接入哪些已安装的扩展包 |
| `data/config/config.json` 的角色配置 | 决定角色是否启用扩展，以及扩展的运行参数 |

项目登记与角色启用统一放在现有配置文件中，不另建注册配置文件。示例仅展示相关字段：

```json
{
  "extensions": ["yuiju-interaction"],
  "characters": {
    "character_a": {
      "extensions": {
        "yuiju-interaction": {
          "enabled": true
        }
      }
    }
  }
}
```

- 包必须先安装并登记，角色才能启用；配置文件不负责安装依赖。角色未声明或未开启时，不创建实例、不向角色提供对应 agent 工具。
- 页面和 API 同样检查目标角色是否启用扩展，不能仅隐藏菜单。
- 增删顶层登记的扩展包或修改能力声明后，重新生成导入表并构建受影响的宿主；前端扩展需要重新构建 Dashboard。
- 已接入扩展的角色开关沿用配置修改后重启生效的约定，不通过开关动态安装代码。
- 扩展运行参数放在角色配置中，具体字段及声明、校验方式后续细化。

### 扩展声明

扩展包不设置 `package.json.exports`，允许直接导入包内任意文件。暂不提前编译 JS，安装产物包含 TS/TSX 源码，由 character-runtime 的 TS 加载器和 Dashboard 的构建工具处理。跨包导入明确写文件扩展名：

```ts
import something from "yuiju-interaction/src/aa/bb.ts";
```

包根目录约定三个独立配置文件，各自 `export default` 一个对象；没有对应能力时不提供该文件。配置内部直接引用实现，不再维护 JSON 声明或 `entry` 路径。

```ts
// agent.ts
import { interactionAgent } from "./src/runtime/interaction.ts";
import { reflectionAgent } from "./src/runtime/reflection.ts";

export default {
  agents: [interactionAgent, reflectionAgent],
};
```

两类 agent 放在同一个 `agents` 列表中，每个定义包含 `id`、`type`（`task` 或 `scene`）、`description` 和执行能力。同步、异步属于宿主的任务调用方式。具体执行接口随宿主调用与 context 一起确定。

```ts
// api.ts
import { speechApi } from "./src/api/speech.ts";

export default {
  apis: [{ path: "/speech", router: speechApi }],
};

// web.ts
import { InteractionPage } from "./src/web/interaction-page.tsx";

export default {
  pages: [{ path: "/", title: "互动", component: InteractionPage }],
};
```

API 的 `path` 位于扩展 API 命名空间下；页面的 `path` 位于扩展页面命名空间下，`/` 表示首页。第一版使用静态路径。工具参数 schema 由实现维护。

三个配置入口按宿主隔离依赖：`web.ts` 不导入 agent 或服务端 API；浏览器专用初始化在组件挂载后执行，避免页面服务端渲染时访问浏览器对象。

### 宿主注册流程

配置始终显式登记包名，不填写目录路径。扩展可以放在 `data/extensions/<目录>/`，也可以安装为项目根目录的依赖：

```bash
pnpm add -w yuiju-interaction
# 仓库内开发的包
pnpm add -w 'yuiju-interaction@workspace:*'
```

```text
读取 data/config/config.json 顶层 extensions 中登记的包
  → 在 data/extensions/*/package.json 中按 name 查找已登记的包
  → 没有本地同名包时，从项目根目录解析 pnpm 安装的包
  → 检查包根目录 agent.ts / api.ts / web.ts
  → 为存在的配置文件分别生成 runtime、Dashboard API、页面导入表
  → 宿主按目标角色配置决定是否启用，再加载对应配置对象
```

本地目录名不要求与包名一致，角色配置继续使用包名。同名本地包优先于已安装包；登记包名对应多个本地目录时报错。本地包已找到但配置有误时直接失败，不切换到已安装包。未登记包不生成导入；扫描到的 package.json 必须是合法 JSON 并包含 name。

本地包使用相对文件路径生成导入，已安装包使用包名子路径；Tailwind 同样扫描实际选中的目录。仅放入本地目录不会安装依赖或建立包名别名，本地扩展内部使用相对导入，所需依赖须另行安装。

生成器位于 `packages/shared/src/extension/generate.ts`，通过 `pnpm run generate:extensions` 执行。生成阶段不导入扩展配置、不执行扩展代码；只检查包信息和约定文件，配置内容由对应宿主加载。完整项目配置及密钥不进入生成文件。

导入表保留字面量路径，例如角色端：

```ts
export const extensionAgents = [
  {
    extension: "yuiju-interaction",
    load: () => import("yuiju-interaction/agent.ts"),
  },
] as const;
```

生成结果分别位于：

```text
apps/character-runtime/src/extensions/generated.ts
apps/dashboard/src/extensions/generated-api.ts
apps/dashboard/src/extensions/generated-pages.ts
apps/dashboard/src/extensions/generated-sources.css
```

生成文件不提交 Git。两个应用的 `dev`、`start`、类型检查命令及 Dashboard 的 `build` 命令显式执行生成；生成失败不继续启动或构建。Dashboard 增删扩展仍须重新构建，启动前生成不会改变已有构建产物。

页面样式扫描来源随登记列表生成：只为提供 `web.ts` 的扩展添加包目录来源。Dashboard 统一加载 Tailwind、shared 主题和生成的扫描来源。

当前实现范围为包发现、配置校验、导入表生成与公共 UI。生成器不校验配置对象内的业务定义、不执行 agent、不挂载 API 或页面；执行契约与 context 确定后接入宿主业务流程。

### 页面与 API 注册

Next.js App Router 仍采用文件路由，没有直接等同于 `router.addRoute()` 的页面注册 API。宿主提供一个动态路由适配入口，通过注册表选择扩展组件，不为每个扩展单独创建 `page.tsx`。

```text
app/(standalone)/extensions/[characterId]/[extension]/[[...path]]/page.tsx
```

例如：

```text
/extensions/character_a/yuiju-interaction
/extensions/character_a/yuiju-interaction/settings
```

访问流程为：确认角色与访问权限 → 确认扩展已启用 → 匹配声明的页面 → 渲染组件。第一版页面使用明确的相对路径，不再实现一套复杂的动态路由语法。

API 由 Dashboard 的 Hono 挂载到 `/api/extensions/<扩展包名>` 下。例如声明中的 `/speech` 对应 `/api/extensions/yuiju-interaction/speech`；角色相关 API 必须校验目标角色及扩展开关。

Next.js 动态路由机制参考：[Dynamic Route Segments](https://nextjs.org/docs/app/api-reference/file-conventions/dynamic-routes)。

## 5. 主 agent 如何发现与调用扩展 agent

采用 skill 式的渐进加载：先提供简短能力目录，需要时再查询使用说明；实际任务执行和场景控制权交接由 runtime 的工具与调度机制负责。参考 [Agent Skills 的渐进加载设计](https://agentskills.io/specification#progressive-disclosure)，第一版不强制采用完整的 skill 文件规范。

### 能力目录

角色初始化时，宿主从已启用扩展的 `agents` 声明生成简短目录，提供给主 agent：

```text
可调用的任务 agent：

- yuiju-reflection/reflection
  根据提供的经历进行反思，返回整理结果。
  支持同步等待或后台执行。

可进入的场景：

- yuiju-interaction/interaction
  与用户进行语音、屏幕和 Live2D 互动。
  进入后由该 agent 接管行动决策。
```

- 调用标识统一为 `<扩展包名>/<agent ID>`，目录与工具参数使用同一标识，避免不同扩展的同名 agent 冲突。
- 主 agent 只感知能力标识、用途及任务/场景类型，不需要了解 npm 包结构、实现路径、API 和页面声明。
- 目录置于稳定的上下文部分，不每轮重新追加，也不一次加载全部详细说明和参数 schema，减少上下文开销并保持缓存前缀稳定。
- 扩展的 `description` 要描述适用场景，不能只写“互动 agent”等泛化名称。

### 三个宿主工具

| 工具 | 参数 | 职责 |
| --- | --- | --- |
| `inspect_agent` | `agentId` | 查询使用说明和输入参数 schema，不启动任务或切换场景 |
| `call_agent` | `agentId`、`mode: "sync" \| "async"`、`payload` | 委托任务型 sub agent |
| `enter_scene` | `agentId`、`payload` | 请求进入场景并交出行动决策权 |

`inspect_agent` 返回详细使用说明、输入参数 schema、结果含义以及进入条件或必要准备。schema 从实现入口读取，与执行校验共用一份定义，不在其他声明中重复维护。

简单能力只需要简述和参数说明；复杂能力可以提供额外使用文档，查询时一起返回。主 agent 按需查询，不要求每次调用前都重复读取，也不强制每个 agent 都编写 `SKILL.md`。

`payload` 使用 JSON 字符串，沿用世界行动的参数传递方式。宿主解析后按目标 agent 的 schema 校验；`call_agent` 只执行 `task`，`enter_scene` 只进入 `scene`，两者都仅允许访问当前角色已启用的能力。

扩展数量增长时，继续复用这三个工具，不为每个扩展 agent 注册一个新工具，也不把所有不同的输入 schema 塞进主 agent 的工具定义。

### 执行流程

```text
主 agent 看到简短能力目录
  → 按需 inspect_agent 了解使用方式与参数
  → 根据能力类型选择 call_agent 或 enter_scene
```

任务调用：

- `mode: "sync"`：宿主等待 sub agent 完成，通过本次工具返回结果。
- `mode: "async"`：工具先返回任务 ID，主 agent 继续运行；完成后宿主将关联任务和调用方的结果事件放入调用方待处理事件集合。
- 两种模式执行同一个任务入口。扩展只返回执行结果，不自行决定向谁投递或维护事件队列。

场景调用：

```text
enter_scene
  → 检查进入条件、准备场景
  → 在安全交接点停止旧 agent 继续提交行动
  → runtime 转移控制权
  → 场景 agent 开始处理事件
```

查询说明或提交进入请求本身不代表已经切换成功。只有条件检查、准备和安全交接完成后才转移控制权；不将进入场景混成普通后台任务调用。

## 6. 扩展 context

`context` 是宿主传给扩展代码的能力接口，不是自动注入 LLM 的全量上下文。它承载与当前角色、扩展实例和执行生命周期有关的能力，按扩展实际需要提供，不暴露整个 Character 或项目配置。数据库连接直接复用 shared，不通过 context 再包装一层。

### 角色与世界状态查询

查询接口在创建扩展实例时绑定角色，调用时不再传 `characterId`，始终使用所属角色的视角。

| 查询内容 | 真相源与提供方 |
| --- | --- |
| 情绪、感受、计划、记忆、自我认知 | character-runtime 对应业务模块 |
| 位置、当前活动、身体状态、资产、天气、地点 | world-simulator |
| 熟悉地点、路线、可选行动与执行条件 | 世界提供的角色视角查询 |

接口方向如 `context.inspectCharacter(...)`、`context.inspectWorld(...)`，具体 TS 签名后续确定。世界查询复用现有 `WorldClient.inspect` 及感知限制，不因调用者是扩展就开放全局世界状态；角色查询复用已有业务模块，不另写一套规则。

扩展代码可按需将这些能力绑定为 function tool，尽量复用宿主已有的工具说明、参数和输出格式。程序获得结构化数据，提供给 LLM 时再进行语义整理和长度限制，不每轮附带全部情绪、计划、记忆及世界状态。

查询与事件配合使用：

- 查询回答“现在是什么状态”，需要时读取。
- 事件表达“发生了什么变化”，由 runtime 路由给接收方，决定是否触发一轮思考。
- 场景进入时查询必要状态，运行中接收相关事件，再按需查询最新状态；扩展不各自轮询世界，也不把每次数值变化都转成模型调用。
- 任务型 sub agent 通常使用调用方提供的任务素材，确实需要时再查询当前状态；不能把任务开始时的素材当成任务结束时的最新状态。

### 状态修改

修改通过宿主注入的业务能力执行，不提供通用 `setState()` 或任意字段写入接口。接口方向例如：

```ts
context.emotion.expressFeeling(...)
context.plans.create(...)
context.plans.update(...)
context.world.executeAction(...)
```

这些接口调用现有业务流程：表达感受经过判断、审查和情绪更新；修改计划同步维护提醒；世界行动由世界检查条件并结算，不直接修改位置或金币。

查询权限与修改权限分开。任务型 sub agent 能查询世界，不代表拥有世界行动权；场景 agent 执行动作时，runtime 必须检查当前控制权，不能只在创建实例时检查一次。读取情绪、计划也不意味着可以直接覆盖它们。

结果明确区分“已提交处理”“已完成修改”“被拒绝”“失败”。同步完成就返回最终结果；需要后台审查的操作先返回受理结果，最终结果通过事件反馈，避免 agent 把提交成功理解为状态已改变。

| 修改对象 | 处理方式 |
| --- | --- |
| 角色、世界业务状态 | 调用宿主注入的业务能力 |
| 扩展自己的临时状态 | 扩展自行管理 |
| 扩展自己的持久化数据 | 从 shared 获取 Redis、MongoDB 连接，由扩展自己的存储模块读写 |

扩展自有数据按环境、角色、扩展隔离，复用现有环境命名规则；角色身份由 context 提供。不额外设计通用 `context.storage` 接口。扩展存储不能成为绕过业务接口访问角色、世界业务数据的通道，也不能保存另一份角色或世界状态作为真相源。

### 其他按需提供的能力

| 能力 | 用途与边界 |
| --- | --- |
| 角色身份 | 角色 ID、名称，及按需获取人设；不附带全部记忆和状态 |
| 扩展配置 | 当前角色为本扩展设置的运行参数，不暴露整个项目配置 |
| 执行生命周期 | 取消信号，响应任务取消、场景退出和进程停止；区分单次执行与整个实例的停止 |
| 事件接入 | 将 ASR、页面操作、外部服务反馈送入自身待处理事件集合，不绕过 runtime 直接启动另一轮模型调用 |
| 页面通信 | 查询页面是否就绪、发送表演指令、接收执行反馈，绑定当前角色与会话 |
| 日志与埋点 | 沿用宿主能力记录运行、错误和耗时 |
| 场景退出 | 仅场景 agent 使用，提交结束原因和过程摘要，由 runtime 完成交接 |

任务结果不需要扩展自己发事件：任务入口直接返回结果，由宿主按同步或异步调用方式交付。事件接入主要服务于外部输入，如 ASR 识别完成、页面播放结束。

### 实例能力与单次执行信息

```text
创建扩展实例
  → 角色身份、扩展配置、业务能力、日志

执行一次任务
  → 任务输入、任务 ID、取消信号

进入一次场景
  → 场景输入、会话信息、取消信号
```

长期可用的实例能力与单次执行信息分开传递。任务 ID、输入、取消信号留在本次执行参数中，不写成扩展实例上共用的可变字段，避免多个异步任务互相覆盖。

### 前后端 context 边界

- runtime 获得角色业务能力，并按需向扩展开放。
- Dashboard API 获得必要的服务能力和角色调用入口；需要角色状态时向目标 runtime 查询或转发，不再创建 Character，也不直接修改其存储。
- 页面只获得可公开的角色信息、资源地址和通信能力，不获得密钥、数据库或服务端配置。

三端不共享同一份 context。日期格式化、schema 工具、已有 LLM SDK 封装等技术能力继续从 shared 的具体路径导入，不为了形式统一全部包装进 context。Redis、MongoDB 连接也由扩展服务端代码直接从 shared 导入，不进入浏览器依赖。

## 7. 页面、API 与角色通信

页面是 agent 的交互终端，HTTP 接口的执行位置按状态归属划分。

| 操作 | 执行位置 |
| --- | --- |
| 读取可用模型资源、调用 TTS 等页面服务 | 可由 Dashboard 挂载的扩展 API 处理 |
| 请求进入互动、提交用户输入、退出场景 | 交给目标角色的 runtime |
| agent 下发表演指令、页面反馈播放结果 | 页面与角色 runtime 的实时连接 |

```text
浏览器中的扩展页面
  ├─ HTTP → Dashboard 挂载的扩展 API
  └─ 实时连接 → 目标角色 runtime → 扩展 agent
```

页面接口不能为了处理请求，在 Dashboard 再创建一份互动 agent 或绕过 runtime 修改其状态。

Live2D、音频等执行反馈区分两层：

- 指令是否被接受：可以作为工具返回值，不必等待整段表演完成。
- 表演完成、播放失败、用户打断：作为后续事件，按场景需要交给 agent。

把消息写入连接不等于表演成功。页面未连接时，工具明确返回不可执行；进入需要页面的场景前，应确认页面就绪。

公开 Dashboard 保持现有访问边界，不因挂载扩展而自动开放角色控制能力。

## 8. 公共 UI、Tailwind 与资源

### UI 依赖

| 能力 | 归属 |
| --- | --- |
| Button、Dialog、Select 等 shadcn 组件 | `shared/src/ui/components/` |
| `cn()` 等 UI 工具 | `shared/src/ui/utils.ts` |
| 颜色、圆角、明暗主题等公共样式 | `shared/src/ui/theme.css` |
| Tailwind/PostCSS 构建入口 | Dashboard |
| Live2D 舞台、互动控制面板及专属样式 | 互动扩展 |

- Dashboard 和扩展引用同一套公共组件。迁出组件时，移除其对 Dashboard 的 `@/lib/...` 等路径依赖。
- 公共 UI 声明实际使用的 Radix、CVA、`tailwind-merge` 等依赖；扩展声明 Pixi、Live2D 等专属依赖。
- React 作为组件包的 `peerDependency`，与 Dashboard 使用同一份运行时。
- Tailwind 由 Dashboard 统一编译，样式入口加载公共主题，通过 `@source` 明确扫描公共组件和已接入扩展的前端源码。
- 扩展不重复加载 Tailwind 基础样式；专属样式可使用 CSS Module。
- shared 的包导出需要支持 UI 的 TSX 和 CSS 具体入口，不能让前端入口间接引入服务端能力。

### 角色资源

```text
扩展包：代码与通用资源
data/live2d/<角色ID>/：角色模型资源
宿主：提供角色配置与模型资源 URL
```

扩展不硬编码悠乃或本地资源路径。Dashboard 与角色服务分开部署时，由实际持有资源的一侧提供访问地址，不假设两者共享文件系统。

## 9. 后续需要细化

- 宿主 context 与各次执行参数的具体 TS 契约，包括能力注入范围、任务执行、事件投递及生命周期；主 agent 的发现与调用方式按上述三个工具设计。
- agent 执行契约、API/页面宿主挂载，以及扩展运行参数的声明和校验。
- 控制权交接的安全边界、场景进入失败与退出异常时的处理，以及各场景具体接收哪些事件。
- 异步任务和场景状态是否需要跨重启保留，重启后如何结束或恢复。
- 多角色 runtime 的实时连接入口、会话识别与访问授权，以及独立部署时的资源访问方式。

先用实际互动场景验证边界，再补充契约，不提前搭建完整插件框架。
