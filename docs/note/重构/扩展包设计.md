# 扩展包设计

包发现、启用配置、导入表生成、公共 UI 与本期扩展 runtime 已实现。本文记录接入契约与执行流程；Dashboard 页面/API 挂载已接入；页面与角色进程通信留待后续实现。

## 1. 职责与接入约定

| 模块              | 职责                                                               |
| ----------------- | ------------------------------------------------------------------ |
| character-runtime | 每进程运行一个角色；装配扩展、调度事件、执行任务、管理行动决策权   |
| 扩展包            | 具体 agent、工具、模型选择、上下文压缩、提示词、页面及专属 API     |
| Dashboard         | 挂载扩展页面与 Hono API，检查部署权限与角色启用状态                |
| shared            | 共用契约、已有 LLM/数据库能力、提示词管理及公共 UI；不执行角色业务 |

- 包名以 `yuiju-` 开头，直接作为扩展标识。
- `config.extensions` 显式登记包名；`config.characters[characterId].extensions[包名].enabled` 决定角色是否启用。配置修改后重启生效。
- 优先按 `data/extensions/*/package.json` 的 `name` 查找，再解析项目根目录 pnpm 依赖。多个本地目录同名时报错，本地包配置错误不切换到已安装包。
- 包根目录约定 `agent.ts`、`api.ts`、`web.ts`，各自默认导出配置对象，没有对应能力就不提供文件。前后端入口不相互导入。
- 扩展不设置 `package.json.exports`，允许直接导入包内文件；暂不提前编译 JS，跨包子路径明确写 `.ts` / `.tsx`。
- 生成器位于 `packages/shared/src/extension/generate.ts`，只发现入口并生成字面量导入，不执行扩展代码。两个宿主运行前、Dashboard 构建前生成；前端声明变化后重新构建 Dashboard。
- 生成物为 runtime 的 `generated.ts`，以及 Dashboard 的 `generated-api.ts`、`generated-pages.ts`、`generated-sources.css`，不提交 Git。
- 扩展不反向导入 `apps/*`，不直接修改角色与世界的存储。扩展自己的数据可以从 shared 获取 Redis/MongoDB 连接，由扩展自己的存储模块管理。

```text
data/config/config.json

data/extensions/<目录>/             # 或安装到项目依赖中
  package.json
  agent.ts
  api.ts
  web.ts
  src/
    config.ts                       # 纯 schema，可被多个服务端入口复用
    protocol.ts                     # 页面与 agent 共用的消息契约
    prompts.ts
    runtime/
    api/
    web/
```

## 2. 本期范围

本期实现扩展 runtime（扩展装配、任务执行、场景进入与退出、事件调度），并接入 Dashboard 的页面与 API 挂载。

- Context 只提供 `character`、`config`，不提前注入世界、记忆、情绪、计划、页面控制等能力；后续按实际需要添加。
- 主 agent 负责准备角色进入场景需要的环境，扩展负责确认用户是否主动进入，宿主负责最终交接控制权。
- 页面/API 挂载见第 10 节；不设计浏览器与角色进程之间的网络连接、端口、认证或场景专属服务。
- 不新增角色级 `runtime.listen_port`、`public_url`、`access_token` 配置。通用 runtime 的执行契约不要求浏览器直接连接角色进程。

## 3. 两类 agent 与声明

| | 任务型 agent | 场景型 agent |
| --- | --- | --- |
| type | `task` | `scene` |
| 作用 | 完成一次委托并返回结果 | 接管角色注意力，持续处理场景事件 |
| 主 agent | 同步调用时等待，异步调用后继续 | 准备环境后等待扩展确认；场景运行期间暂停决策 |
| 实例 | 每角色、每 agent 创建一个，随角色停止销毁 | 每次准备进入时创建，进入失败或退出后销毁 |
| 并发 | 不同任务可并发，单次数据通过执行参数传入 | 同一角色只有一个准备中或运行中的场景，轮次串行 |

`agent.ts` 默认导出 `configSchema`、`agents`，以及可选的 `prompts`。任务和场景放在同一个 `agents` 数组中，通过 `type` 区分。

| 字段 | 含义 |
| --- | --- |
| `id` | 包内唯一标识，对外使用 `<包名>/<id>` |
| `type` | `task` 或 `scene` |
| `description` | 简短用途，用于主 agent 的稳定能力目录 |
| `instructions` | 可选详细说明，按需查询；场景需说明主 agent 应提前准备什么 |
| `create` | 接收 Context，创建当前角色的执行实例 |
| `inputSchema` | 仅任务型 agent 提供，校验任务参数 |
| `resultDescription` | 仅任务型 agent 提供，说明执行结果的含义 |

场景不设计通用业务 `payload` 和 `inputSchema`，进入时只接收主 agent 传来的可选上下文。扩展自己的操作参数由扩展维护，不要求主 agent 代用户填写。

场景可声明 `pauseConversation`、`worldEvents`、`eventSchema`，分别表示是否暂停新聊天轮次、接收哪些普通世界事件、允许哪些扩展自定义事件。去掉 `requiresPage`，宿主不规定场景必须以哪种界面运行。

## 4. Context 与执行参数

```ts
type ExtensionContext<Config> = {
  readonly character: Readonly<{
    id: string;
    name: string;
  }>;
  readonly config: Readonly<Config>;
};
```

- `character` 只提供当前角色的身份，不直接暴露 Character 实例及其内部模块。
- `config` 是当前角色为本扩展配置、并经过扩展 schema 校验的参数，不包含整个项目配置。
- Context 在创建实例时注入，不自动变成 LLM 上下文。
- 任务 ID、场景 ID、取消信号属于执行参数，不放进 Context，也不作为共享任务实例上的可变字段。
- logger、埋点、LLM、数据库、日期工具、`renderPrompt` 直接从 shared 的具体模块导入，不额外包装。
- 扩展自己的数据自行管理；不能因为能取得数据库连接，就绕过宿主直接修改角色与世界的业务数据。

本期不增加 `TaskContext`、`SceneContext` 两套业务能力集合，也不实现扩展之间的嵌套委托。确实需要新的角色能力时，再单独确定接口及边界。

### Context 的创建与注入

注入方是 `character-runtime/src/extensions/` 中的扩展宿主。扩展包导出 agent 定义和 `create` 工厂，宿主通过普通函数参数显式注入，不使用全局 Context、隐式单例或自动依赖注入。

```text
Character 初始化扩展宿主，提供自己的 id、name 和扩展配置
  → 宿主筛选该角色已启用的扩展
  → 从生成的导入表加载 agent.ts 的默认导出
  → 剔除 enabled，用扩展的 configSchema 校验参数
  → 为“当前角色 + 当前扩展”创建 runtimeContext
  → 汇集默认提示词并应用 data/prompt 覆盖
  → 任务型：调用 agent.create(runtimeContext)，保存返回的实例
  → 场景型：先保存定义与 runtimeContext，准备进入时再调用 create
```

宿主侧的核心调用如下。`character` 来自当前 Character，`parameters` 是移除 `enabled` 后的扩展配置，`definition` 是扩展入口的默认导出：

```ts
const runtimeContext = {
  character: { id: character.id, name: character.name },
  config: definition.configSchema.parse(parameters),
};

const instance = agent.create(runtimeContext);
```

`create` 的返回类型按 agent 类型区分：

```ts
// 任务型定义的工厂
create(context: ExtensionContext<Config>): TaskInstance<Input>;

// 场景型定义的工厂
create(context: ExtensionContext<Config>): SceneInstance;
```

- 扩展的 `create` 可以通过函数闭包或实例字段持有 Context；后续 `run`、`waitForEntry`、`handleEvents` 直接使用，不需要每次重新加载配置或再次注入。
- 同一角色、同一扩展的多个 agent 可以共用这份只读 Context；不同角色分别创建，不把角色数据写进包级全局变量。
- 任务实例创建后复用；每次准备进入场景都创建新实例，但仍使用该角色已校验的扩展 Context。
- `create` 只装配实例，具体异步执行放在生命周期方法里。模块导入时不启动任务、创建角色实例或调用模型。
- `runtimeContext` 是程序依赖；`enter_scene` 的文本 `context` 是本次交接内容，两者分别通过 `create(runtimeContext)` 和 `waitForEntry(context, execution)` 传入。

## 5. 主 agent 的发现与调用

初始化时把已启用 agent 的标识、类型和 `description` 放入稳定能力目录。详细说明按需查询，不复制主 agent 全量上下文。

| 工具 | 参数 | 行为 |
| --- | --- | --- |
| `inspect_agent` | `agentId` | 查询用途、使用说明；任务返回参数 schema，场景返回环境准备要求 |
| `call_agent` | `agentId`、`mode: "sync" \| "async"`、`payload` | 调用任务型 agent |
| `enter_scene` | `agentId`、可选 `context` | 告知宿主环境已准备好，申请等待扩展确认进入 |

`call_agent.payload` 保留 JSON 字符串，按目标任务的 schema 解析校验。`enter_scene.context` 是普通文本，不要求模型生成 JSON。

进入上下文说明当前情况、已完成的准备、用户意图，以及接下来需要场景注意的事项。例如：

```text
用户约好现在进入这个场景。我已经回到家，手头的事情处理完了。
刚才讨论的是周末出行，可以接着这个话题。
```

这段文本只是交接信息，不是完整主 agent 历史，也不能代替用户点击。`enter_scene` 返回“已准备，等待扩展确认”，不表示已经进入。

## 6. 任务型 agent 执行

```ts
type TaskExecution = {
  taskId: string;
  signal: AbortSignal;
};

type TaskInstance<Input> = {
  run(input: Input, execution: TaskExecution): Promise<JsonValue>;
  dispose?(): Promise<void>;
};
```

`JsonValue` 复用现有 JSON 数据类型，`Input` 从任务 schema 推导。

```text
call_agent
  → 校验目标、类型与参数
  → 创建 taskId，记录原调用方
  → instance.run(input, execution)
     ├─ sync：等待完成，结果通过本次工具返回
     └─ async：先返回 taskId，完成后向原调用方投递结果事件
```

- 同步和异步执行同一个入口；等待方式与结果投递由宿主负责，扩展只返回结果。
- 异步事件包含 `taskId`、`agentId`、成功/失败状态及结果或错误；模型不填写接收方。
- 主 agent 进入场景后，先前发起的异步任务仍可完成，结果留在主 agent inbox，等它恢复后处理。
- 同步任务随本轮取消，异步任务随进程停止取消。外部请求传递取消信号，沿用已有请求超时，不新增自动重跑队列。
- 失败通过工具结果或事件明确返回，不自动重试，不把失败改写成正常结果。

## 7. 场景执行与控制权交接

### 执行契约

```ts
type SceneExecution = {
  sessionId: string;
  signal: AbortSignal;
};

type SceneRoundResult =
  | { status: "continue" }
  | { status: "exit"; reason: string; context?: string };

type SceneInstance = {
  waitForEntry(
    context: string | undefined,
    execution: SceneExecution,
  ): Promise<
    | { status: "confirmed" }
    | { status: "rejected"; reason: string }
  >;
  handleEvents(
    events: SceneEvent[],
    execution: SceneExecution,
  ): Promise<SceneRoundResult>;
  dispose(): Promise<void>;
};
```

- `waitForEntry` 在主 agent 准备好之后执行。扩展只有确认用户主动点击进入、且自身准备完成后才返回 `confirmed`；创建实例或资源就绪本身不能触发确认。
- 用户取消或扩展无法进入时返回 `rejected`。输入如何从用户界面到达扩展，留给后续接入设计；这里不预设 HTTP、WS 或连接票据。
- `confirmed` 表示扩展确认可以交接，最终转移控制权仍由宿主执行，扩展不直接修改控制状态。
- `handleEvents` 执行一轮场景思考，可以通过 AI SDK 按需连续调用工具；返回 `continue` 只表示本批处理完成，不结束场景。
- 场景决定退出时，先完成当前模型步骤及工具结果，再返回 `exit`。普通业务工具不作为轮次或场景结束标识。
- `dispose` 释放本次实例的资源，不生成总结、不发起新的业务操作。

这些是宿主调用扩展的生命周期方法，不往 Context 中增加控制接口。

### 进入流程

控制状态由 `agent-loop/control.ts` 统一管理：

```text
main
  → waiting_entry：主 agent 已准备好，等待扩展确认
  → scene：用户主动进入，扩展确认，宿主完成交接
  → exiting：场景结束并释放资源
  → main

waiting_entry
  → 拒绝 / 超时 / 准备异常
  → 释放实例，回到 main
```

1. 主 agent 根据场景说明，通过现有工具准备好相关环境。若仍需等待移动或其他活动完成，就继续正常处理事件，不提前调用 `enter_scene`。
2. 准备完成后调用 `enter_scene(agentId, context?)`，宿主登记等待进入的请求并生成 `sessionId`。同一角色不重复创建第二个准备实例。
3. 当前 SDK 步骤的工具执行与结果保存完成后，主 agent 暂停新决策；创建场景实例，进入 `waiting_entry`。
4. 宿主调用 `waitForEntry` 并开始计时。扩展等待用户主动进入，准备期间不运行场景 agent。
5. 扩展返回 `confirmed` 后，宿主确认本次等待仍有效，再将控制权交给该 scene，并投递首次进入事件。此时场景才开始执行。
6. 用户取消、扩展拒绝、准备报错或等待超时，都结束本次准备并释放实例；宿主向主 agent 投递未进入原因，恢复主 agent，不自动重新申请。

进入等待固定超时为 30 分钟，不新增配置项。计时覆盖 `waitForEntry` 的整个等待过程；超时后取消其信号，结束本次 session，迟到的确认不能重新激活场景。

安全交接点仍是完整模型步骤及其工具副作用完成之后。`waiting_entry` 期间主 agent 已暂停，但 scene 尚未获得决策权；世界继续运行，宿主继续接收事件和同步状态。

### 退出与返回上下文

场景退出可以携带一段 `context`，通过结束事件交给主 agent。例如：

```text
这段时间和用户讨论了周末出行，已经确定周六上午去公园。
用户临时有事先离开了，约好下次再聊交通安排。
```

- `reason` 描述为何结束；可选 `context` 描述这段时间发生了什么、重要结论和未完成事项，不默认传递完整场景历史。
- 宿主收到 `exit` 后停止调度该场景，释放实例，再把 `agentId`、`sessionId`、原因和上下文投递给主 agent。
- 主 agent 将结束事件作为下一轮输入，不把场景上下文覆盖成系统提示词，也不据此重放场景行为。
- 扩展运行异常时由宿主结束场景并返回实际错误；没有总结就不附带总结，不临时再调用模型补造。
- 释放资源失败记录错误，但不让主 agent 永久卡在场景中。旧 session 失效，不再接收后续输入。
- 已经完成的外部副作用不会因为退出而撤销。宿主不自动重启失败场景，也不自动重新执行主 agent 的准备动作。
- 本期不支持场景嵌套或直接切换；先退出到 main，再准备下一个场景。

### 与聊天的关系

场景声明的 `pauseConversation` 在等待进入和场景运行期间生效，只限制新 Planner 轮次，已开始的轮次继续完成。

准备失败或场景退出后只解除这项限制，不覆盖手动群开关和睡眠状态。恢复聊天沿用既有的暂停背景整理策略。

## 8. 事件与调度

- 普通输入先进入 inbox。一轮取固定批次，执行期间到达的事件留到下一轮；不在输入回调里直接调用模型。
- 宿主负责串行调用 `handleEvents`，扩展负责该轮的模型、工具、上下文和压缩策略，不再另起一套 inbox 轮询。
- `SceneEvent` 包含宿主维护的 `id`、`occurredAt`、`type` 和 `payload`。扩展自定义事件按自身 `eventSchema` 校验，不得冒充宿主事件。

| 输入 | 处理方式 |
| --- | --- |
| 世界活动、天气事件 | 宿主先同步实际状态、活动等待与聊天权限，再按控制状态路由 |
| `waiting_entry` 期间的事件 | 继续接收，暂不触发决策；确认后按接收规则处理，准备失败则交回 main |
| 场景接收的世界事件 | 进入 scene inbox，不再重复驱动 main |
| 场景未订阅的普通世界事件 | 完成必要状态同步后消费，退出时不逐条重放 |
| 计划到点、活动超时检查 | 宿主继续计时，场景运行时交给当前 scene |
| 聊天通知及主 agent 发起的异步任务结果 | 保留在 main inbox，恢复后处理 |
| 扩展自定义输入 | 仅有效 scene session 可接收，进入场景下一批输入 |

世界连接、状态同步、计划与活动计时属于角色宿主，不能因主 agent 暂停而停止。第一版保留世界连接现有订阅，在 runtime 内筛选模型可见事件，避免同时丢掉活动结束等必要状态同步。

现有世界事件没有紧急级别，不按文案猜测。未来增加具体紧急事件类型时，再明确交给当前控制者的规则，不提前设计泛化的紧急级别配置。

场景内部事件的来源与业务含义由扩展定义；本期不展开具体场景的输入、输出和交互表现。

## 9. 配置与提示词

### 配置

```json
{
  "extensions": ["yuiju-demo"],
  "characters": {
    "character_a": {
      "extensions": {
        "yuiju-demo": {
          "enabled": true
        }
      }
    }
  }
}
```

- 宿主管理 `enabled`，其余字段由扩展 `configSchema` 声明。宿主剔除 `enabled` 后校验，再通过 Context 注入扩展。
- 角色未启用时不创建实例，不向主 agent 暴露对应能力。
- 配置错误在装配阶段明确报出角色、扩展及字段，不静默替换成其他配置。
- 本期不预设扩展的业务参数，也不增加连接、认证或部署相关配置。

### 提示词

- 扩展默认提示词跟随扩展维护，通过可选 `prompts` 列表交给宿主汇集，不让 shared 的固定清单反向导入扩展包。
- 初始化顺序：加载声明 → 汇集 shared 与扩展默认模板 → 应用 `data/prompt` 覆盖/新增 → 创建业务实例。
- key 保留点号分组和下划线段名，例如 `extension.yuiju_demo.task`。角色专属内容仍可使用 `.<characterId>` 后缀。
- 所有业务通过 `renderPrompt` 读取。data 文件优先级最高，缺 key、缺变量沿用当前规则；不在入口模块导入时渲染提示词或调用模型。

## 10. Dashboard 页面与 API

宿主按生成的导入表加载 `web.ts`、`api.ts`；不执行 `agent.ts`，不在 Dashboard 创建角色 agent。

### 页面声明

`web.ts` 默认导出 `ExtensionWebDefinition`（`shared/extension/web`）：

```ts
{
  pages: [{
    id: "demo",
    title: "Demo",
    access: "private", // public 或 private，必须明确声明
    component: DemoPage,
  }],
}
```

- 页面 ID 在包内唯一、非空且不含 `/`。
- 页面地址为 `/extensions/<包名>/<角色ID>/<页面ID>`，由一个 Next.js 动态页面挂载，使用 Dashboard 布局。
- 宿主在服务端筛选角色已启用、且当前部署可访问的页面，生成“扩展”菜单；直接访问地址也执行同样的检查。
- 组件接收 `character: { id, name }` 与 `apiBasePath`，不接收完整角色配置、插件配置或任何服务端实例。
- 交互组件自行声明 `"use client"`，通过 shared 的具体路径引入 shadcn 组件。`web.ts` 及其依赖不得导入 API、数据库或配置加载模块。
- Tailwind 使用生成的 `generated-sources.css` 扫描已登记插件；页面声明变更后重新生成并构建。

### API 声明

`api.ts` 默认导出 `ExtensionApiDefinition<Config>`（`shared/extension/api`）：

```ts
{
  access: "private",
  configSchema,
  create(context) {
    return new Hono().get("/", (c) => c.json({ character: context.character }));
  },
}
```

- API 地址为 `/api/extensions/<包名>/<角色ID>/*`。插件内部从 `/` 声明路由，无需复制宿主路径前缀。
- 宿主确认扩展已登记、角色存在且启用、部署允许访问后，剔除 `enabled` 并按 `configSchema` 校验配置，再调用 `create({ character, config })` 装配本次请求的 Hono 路由。
- `create` 只装配路由，不启动后台任务、不初始化另一份角色。agent 与 API 可从插件内部同一文件导入配置 schema。
- 页面和 API 各自声明访问范围：公开部署只开放明确标记为 `public` 的入口；私有入口、未知角色、未启用扩展都返回 404。隐藏菜单不能代替 API 检查。
- 未处理的 API 异常交给 Dashboard 统一处理；插件自己的错误处理保留。

`data` 下的本地插件可以解析项目根包提供的 `@yuiju/shared`、React 等依赖，并在自身 `package.json` 声明 peerDependencies；其余外部依赖仍由插件正常声明和安装。插件内部 TS/TSX 使用明确扩展名。

### 本地 Demo

`data/extensions/yuiju-demo` 提供三个入口：`echo` 任务支持同步、异步调用；私有 Demo 页面向私有 `/echo` API 发送文本，返回当前角色名称及插件配置的 `prefix`。Demo 不调用模型、不写数据库。项目配置登记 `yuiju-demo`，对应角色配置启用并填写 `prefix`。

页面调用插件 API 与主 agent 调用插件任务是两条独立链路。本期未增加 Dashboard 到 character-runtime 的跨进程命令通道，不提供从页面直接启动角色任务或确认场景进入的能力。

## 11. 失败、停止与重启

本期不保存可恢复的扩展任务或场景执行进度。接受中断损失，避免重放模型与工具调用造成重复副作用。

| 状态 | 保存方式 | 重启后行为 |
| --- | --- | --- |
| 扩展声明与角色配置 | 配置文件 | 重新读取、校验和装配 |
| 进入等待、控制权、活动 scene | 内存 | 回到 main，旧 session 失效 |
| 运行中的任务、场景上下文及输入 | 内存 | 丢弃，不续跑，不补造结果 |
| 已投递给主 agent 的完成/退出事件 | 现有主 agent inbox | 按现有事件机制处理 |
| 已完成的业务修改或扩展持久化结果 | 对应业务模块 | 保留，不自动恢复原执行 |

停止时拒绝新调用、取消进入等待及运行中的执行，再释放实例。任务失败、进入失败和场景异常都明确返回结果，不自动重试，不引入后台无限投递队列。

## 12. 完整流程

```text
主 agent 了解场景要求
  → 使用现有能力准备好环境
  → enter_scene(agentId, context?)
  → 完成本步工具，暂停主 agent
  → 创建实例，waitForEntry，等待扩展确认
     ├─ 用户主动点击进入，扩展确认
     │   → 宿主交出控制权，scene 开始处理事件
     │   → 场景结束，返回 reason 和可选 context
     │   → 释放实例，将结束事件投递给 main，恢复决策
     └─ 拒绝、超时或准备异常
         → 释放实例，将未进入原因投递给 main，恢复决策
```

## 13. 实现位置

| 文件或模块 | 职责 |
| --- | --- |
| `packages/shared/src/extension/agent.ts` | 扩展声明、Context、任务与场景执行契约 |
| `packages/shared/src/extension/api.ts`、`web.ts` | Dashboard API 与页面声明契约 |
| `dashboard/src/extensions/server.ts` | 可访问页面列表，供菜单和动态页面使用 |
| `dashboard/src/app/(dashboard)/extensions/[extension]/[characterId]/[pageId]/page.tsx` | 挂载已启用的扩展页面 |
| `dashboard/src/app/api/[[...route]]/routes/extensions.ts` | 校验访问范围、注入 Context、分发插件 API 请求 |
| `packages/shared/src/prompt/template.ts` | 汇集扩展默认提示词，应用本地覆盖 |
| `character-runtime/src/extensions/load.ts` | 加载已启用扩展、校验配置、组装 Context |
| `character-runtime/src/extensions/runtime.ts` | 任务实例、同步/异步调用、取消与结果投递 |
| `character-runtime/src/extensions/tools.ts` | 主 agent 的三个扩展工具 |
| `character-runtime/src/agent-loop/runtime.ts` | 当前控制者的事件调度与批次隔离 |
| `character-runtime/src/agent-loop/control.ts` | 进入申请、等待确认、场景执行与退出 |
| `character-runtime/src/agent-loop/attention.ts` | 独立于模型执行的活动和计划计时 |
| `character-runtime/src/agent-loop/main.ts` | 一批主 agent 输入的模型执行和上下文保存 |
| `character-runtime/src/character.ts` | 装配实例、投递结果、同步世界状态与聊天许可 |

`Character.receiveSceneEvent(sessionId, input)` 是扩展自定义事件的程序入口；当前不提供网络路由。用户进入由扩展自己的 `waitForEntry` 确认。角色入口传入固定的 30 分钟进入等待时间，不增加配置项。
