# 临时真实运行测试方案

## 1. 目标与方式

验证 character-runtime 与 world-simulator 的主要执行链路是否正常，以及角色的实际行为是否符合产品预期。测试过程同时帮助理解事件、模型、工具、状态和持久化之间的关系。

- 不使用 Vitest，不新增单元测试或长期维护的测试框架。
- 两个应用使用独立进程，调用真实 LLM、Redis、MongoDB、HTTP、WebSocket 和 BullMQ。
- 不 mock 模型、替换模型回答、修改提示词强迫行动，或绕过正常业务流程制造成功结果。
- 使用真实时间和已有活动持续时间，不修改系统时钟或缩短生产规则。一个活动闭环可能需要十几分钟。
- 临时脚本负责组织场景、控制进程、汇总记录；业务执行仍由现有应用负责。

无需新增 monorepo app 或 package。临时脚本放在已被 Git 忽略的 `.devtools/e2e/`；现有代码仅补必要的临时日志，不新增业务配置、接口或 tracing 框架。

运行环境固定为项目已有的 `NODE_ENV=development`，不是 `NODE_ENV=dev`，也不新增 `test` 或 `e2e` 环境。测试脚本启动的两个应用子进程均显式设置该值。

测试方案已获授权，临时脚本与日志记录点已实现。运行结果见文末；业务缺陷的修复另行确认。

## 2. 分阶段范围

### 第一轮：主 agent 与世界闭环

覆盖启动连接、事件接收、模型思考、工具调用、活动开始与结束、世界结算、通知确认、Mongo 归档、运行状态恢复。

第一轮先跑正常流程，再跑事件积压和重启场景。暂停服务属于单独场景，避免把故障干扰混入正常流程。

### 后续轮次

| 范围 | 需要观察的主要链路 |
| --- | --- |
| 群聊 | 白名单接收 → trigger → Planner 工具调用 → Replyer → 分段发送；同时观察等待、戳一戳和向主 agent 传递事件 |
| 情绪 | 主 agent 描述感受 → 情绪更新处理 → 数值变化 → 角色可读描述；同一件事频繁表达是否被更新策略控制 |
| 日程 | 创建、修改计划 → 到期事件 → 主 agent 自主决定 → 计划状态变化；到期不等于直接执行行动 |
| 记忆 | 经历记录 → 原材料归档 → 每日整理 → 经历记忆、自我认知、人物画像 → 按需回忆 |

本次不追求覆盖所有地点和活动。互动场景、未实现的表情包发送、长期遗忘、30 天过期、供应商故障切换和达到压缩阈值的长上下文不属于第一轮覆盖范围。

## 3. 运行前检查

### 先准备应用配置

新应用读取 `data/config/config.json`，根目录的旧 `yuiju.config.json` 仅作为现有连接信息与供应商配置的来源，不作为新的加载入口。

- 沿用新配置 schema：`version`、`app`、`database`、`llm.models`、`characters`；旧配置中的字段按新结构转换，凭据不打印到终端或报告。
- 第一轮启用已有世界定义对应的 `yuuno`，中文姓名为雨泽悠乃，昵称为悠乃、悠酱；不配置 OneBot，避免在世界联调时向真实群聊发送消息。
- 世界连接地址使用已有默认值 `http://127.0.0.1:48100`，时区沿用项目配置。
- `chat`、`strong`、`flash` 的供应商放入各自的 `providers`；窗口放在模型组的 `context_window_tokens`，不放在供应商中。
- 已确认沿用旧配置中的模型供应商与数据库连接。chat、strong、flash、multimodal 的压缩预估窗口统一配置为 `1000000` tokens；embedding 不配置该窗口。
- 旧 vision 供应商转换为 multimodal，仅声明原有的 image 输入能力，不额外声明音频、视频能力。供应商的 Structured Outputs 能力没有依据时不声明支持，使用项目已有的非结构化输出处理路径。
- 配置文件本身不保存运行环境；development 由进程的 `NODE_ENV` 指定。

### 检查配置与数据

1. 检查现有开发配置是否具备所需模型、数据库连接、角色配置及世界连接地址；缺项明确列出，不填入临时兜底值。
2. 确认 Redis、MongoDB 可连接，世界监听端口未被其他实例占用，避免同时启动两套实例修改同一份状态。
3. 使用项目已有 development 环境隔离：Redis 使用 `yuiju:dev:` 前缀，Mongo 使用开发 collection 名称。不得运行 `FLUSHDB` 或删除其他数据。
4. 记录本轮开始前的相关 Redis 状态、Mongo 记录和角色记忆文件。配置与记忆文件目前并未按 dev/prod 隔离，不能把 development 当成完整的数据沙箱。
5. 默认沿用当前开发状态，记录其作为起点。若需要验证全新初始化，单独列出要清理的精确 key、collection 和文件，确认后执行。
6. 测试会产生真实模型请求、数据库记录和记忆文件更新。保留记录供复查，不在结束时自动回滚整套数据库。

## 4. 输入输出与可视化

### 记录什么

| 执行阶段 | 记录内容 |
| --- | --- |
| 事件进入 | 来源、类型、事件 ID、发生时间、接收时间、实际 payload、进入哪一轮 |
| 模型请求 | 最终发送的 messages、工具定义、模型与供应商、思考强度及其他请求参数；记录配置合并后的实际请求体 |
| 模型返回 | 返回文本、可获取的 reasoning、工具调用、结束原因、usage、耗时与错误；供应商未返回的字段明确为空 |
| 工具执行 | 工具名、参数、开始与结束时间、实际返回值、错误；工具产生的副作用单独标明 |
| 世界交互 | HTTP 查询与行动请求、响应、活动 ID、开始与结束时间、结算结果及小插曲 |
| 通知与归档 | 入队、WS 发送、角色保存事件、ACK、通知任务完成、Mongo 实际写入完成、失败重试 |
| 状态提交 | 与本次场景相关的状态变更和提交结果，包括活动、待处理事件、agent 轮次、上下文、活动等待 |
| 恢复运行 | 重启前后的状态、恢复到哪一阶段、是否继续未完成操作、是否出现重复业务副作用 |

不打印密钥、Authorization 或包含凭据的连接地址。模型实际上下文完整保存，不用摘要替代原始输入；报告首页仅展示简要说明，展开后再显示详情。

不记录每秒 tick 的重复状态，也不记录所有数据库底层命令。重点是业务边界与实际提交结果，避免大量噪声掩盖流程。

### 如何展示

- 控制台：简短实时进度，显示正在运行的场景、关键步骤、等待原因与异常。
- `trace.jsonl`：每行一条结构化记录，保留完整输入输出与过程。
- `report.html`：本地时间线，按场景、应用、角色和轮次查看；点击展开模型上下文、工具参数、返回值与状态变化。
- 汇总：每个场景的实际结果、证据位置、发现的问题及未覆盖部分。

### 日志等级与输出隔离

E2E 详细记录统一使用现有 Winston 的 `silly` 等级；普通开发运行是 `debug`，生产运行是 `info`，均不会输出这些详细记录。E2E 所发现的真实业务异常仍走现有 warn/error 日志，不隐藏正常错误。

测试入口初始化正常 logger 后，仅在测试进程中增加独立的结构化文件 transport，等级设为 `silly`，输出到 `.devtools/e2e/output/<本轮时间>/`。不通过提高整个 logger 的等级来打开详细记录，正常控制台和应用轮转文件保持原等级。

| 运行方式 | 正常应用日志 | E2E 详细输入输出 |
| --- | --- | --- |
| 普通 dev | debug 及以上，沿用应用日志文件 | 不输出、不写文件 |
| 普通 prod | info 及以上，沿用应用日志文件 | 不输出、不写文件 |
| E2E，环境仍为 development | 沿用 dev 日志等级 | 仅写入临时测试目录，由脚本生成时间线 |

昂贵的记录内容构造，例如完整状态拷贝或响应体读取，应仅在 `logger.isLevelEnabled("silly")` 时执行，避免普通运行为了被过滤的日志额外处理数据。不读取响应正文来替代业务消费，记录需要使用独立副本。

关联优先使用已有的 characterId、roundId、toolCallId、requestId、activityId、eventId 和 jobId；日志额外标明来源进程。时间排序用于阅读，不替代 ID 和调用关系作为因果依据。

记录必须区分“准备执行”“执行成功”“持久化成功”。WS ACK 表示角色已保存事件，不表示主 agent 已处理完；队列入队也不等于 Mongo 已归档。

示例时间线：

```text
角色连接世界
  → 保存 connected 事件
  → 主 agent 取出本轮事件
  → 请求模型：展开提示词、历史上下文、本轮事件与工具定义
  → inspect_world：展开参数与角色可感知的世界信息
  → execute_action：展开参数、实际响应和活动时间
  → 世界活动完成：展开结算与小插曲
  → 归档、通知分别入队
  → WS 发送 → 角色保存事件 → ACK → 通知任务完成
  → 主 agent 开始下一轮
  → Mongo 归档成功（与通知独立，可能先于或晚于通知完成）
```

## 5. 第一轮场景与判断标准

| 场景 | 操作与输入 | 预期与证据 |
| --- | --- | --- |
| 启动、连接 | 启动世界，再启动角色 | 世界加载或初始化状态；角色连接成功；connected 进入主 agent；模型请求带入对应事件 |
| 世界查询 | 观察主 agent 按需查询世界 | 返回当前位置、活动、地图及行动信息；信息符合角色感知范围，不暴露全局状态 |
| 开始行动 | 观察模型自主选择并提交已有活动 | 实际参数符合该 action schema；世界返回权威结果；角色同步活动和等待时间；拒绝的请求不能被模型当成成功 |
| 活动完成 | 等待真实结束时间 | 世界一次结算包含小插曲；按既定流程提交状态、归档与通知；角色获得活动完成事件，活动等待被清理 |
| 思考期间新事件 | 模型请求进行时，经现有事件入口追加一个明确标注的测试事件 | 当前轮不中断；新事件进入下一轮；报告能看到两轮各自的事件集合 |
| 角色离线期间通知 | 停止角色，保持世界运行至活动完成，再启动角色 | 待通知任务保留；重连后发送、保存、ACK；角色处理积压事件，重复投递不产生重复事件处理 |
| 世界重启 | 在活动进行中停止并重启世界 | 活动沿用原 ID 和结束时间；未结束的活动继续；超过结束时间的活动按正常补算规则处理 |
| 角色重启 | 在活动进行中正常停止并启动角色 | 已保存上下文、待处理事件和活动等待恢复；重连查询当前活动，不凭本地倒计时断言已完成 |
| 轮次异常中断 | 在可观测的轮次中终止角色进程，再启动 | 未完成轮次接续；已确认的操作不重复执行；未确认的操作按现有 requestId 与恢复规则处理。若未命中目标阶段，标为未覆盖 |
| 活动结束兜底 | 活动开始后暂停世界，等待角色的检查时间 | 在 `startedAt + 1.5 × duration` 产生一次 activity_due；模型知道结束尚未确认；不每分钟反复产生检查事件；恢复世界后通过真实通知或查询确认状态 |

同一角色前一条通知未 ACK 时，后一条仍应尝试发送。该场景需临时 WS 客户端延迟第一条 ACK，观察第二条的到达时间；它验证通知协议，不计为真实 Character 已处理的场景，单独执行。

模型不一定在某轮选择所需行为。没有触发就记录“未覆盖”，不把脚本直接请求世界执行行动算作主 agent 自主行动通过。必要时可单独通过现有 HTTP 接口验证世界协议，报告明确区分两种来源。

## 6. 执行顺序

1. 检查依赖与起始状态，建立本轮记录目录。
2. 临时记录点就绪后，启动两个独立应用进程，收集正常启动与首轮模型请求。
3. 先观察一个真实活动闭环；核对模型输入、工具结果、世界状态、通知与归档。
4. 分别执行新事件、离线积压、世界重启、角色重启场景，每次记录明确的场景起止。
5. 独立执行异常中断、通知不阻塞和活动结束兜底场景，不与正常场景混跑。
6. 汇总报告并正常关闭进程。测试控制器的超时只标记场景未完成，不向业务注入活动完成事件。

每日记忆整理目前按项目时区在 04:00 运行，并在启动时检查待补任务。后续测试优先观察真实待整理材料及启动补做；若没有到期材料，就等待实际周期或另行确认专项测试方式，不改日期制造已通过结果。

## 8. 结果与收尾

- **符合预期**：业务链路有完整证据，实际状态与模型可见信息一致。
- **系统问题**：执行、状态、持久化、通知或恢复出现错误，记录具体断点和输入输出。
- **角色行为需讨论**：系统执行正确，但模型选择、表达或信息使用不符合预期，保留完整上下文供判断。
- **未覆盖**：条件未出现、模型未选择相关行为、目标中断阶段未命中或观察时间不足。

最终报告逐项给出结果，不用“没有报错”或“所有进程还在运行”代替通过判断。

临时日志改动完成后执行项目格式、lint 和受影响包的 type-check；这些仅验证改动质量，不代替真实联调。

测试结束后保留报告供 review；确认完成后移除本次临时记录点与脚本，只移除本次新增内容，不回退已有业务改动。测试数据清理另行列出精确范围，不自动删除角色记忆或开发数据库。

### 阻塞问题

原 inspect_world 工具 schema 的根是 `oneOf`，缺少根对象的 properties。同一真实供应商的小型诊断中，原 schema 返回 `{}`，根 object schema 返回 `{"type":"current"}`。角色运行中记录了 19 次工具参数错误。
