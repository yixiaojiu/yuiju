# 技术方案

## 对话模块

本文记录对话模块的实现方案。集中确认清单中的用户修改已同步到正文；数据库读写、表情包执行等明确延期内容保留待实现接口。

### 目标与范围

- 第一版接入 QQ 群聊，支持多个角色、每个角色同时参与多个群聊。
- 采用 Planner + Replyer：Planner 决定是否参与、表达什么、采取什么聊天行动，Replyer 负责具体文字表达。
- 第一版实现文字回复、引用回复、等待、戳一戳和继续旁听；表情包只定义 function tool，具体逻辑暂不实现。
- 消息正文采用 Satori XHTML，避免把嵌套消息节点完整序列化为 JSON 提供给模型。
- 角色是生活在虚拟世界中的数字生命，聊天不接管生活决策，不自行执行世界行动、修改计划或作出助理式提醒承诺。
- 私聊、其他平台、dashboard 提示词编辑与数据库人设管理暂不实现。

### 模块职责

| 模块                             | 职责                                                       |
| -------------------------------- | ---------------------------------------------------------- |
| `character-runtime/conversation` | 会话隔离、消息队列、Planner、Replyer、行动执行、聊天上下文 |
| `character-runtime/character.ts` | 角色身份建模，管理所属业务模块的启动与停止     |
| `shared/prompt`                  | 集中维护提示词定义，按 key 获取并替换变量                  |
| `shared/llm`                     | 模型调用、供应商切换与冷却、结构化输出能力                 |
| OneBot 接入                      | 将平台事件转换成聊天消息，执行文字、图片和戳一戳等平台操作 |

业务 loop 不持有 Satori Session。平台接入层提供消息和发送能力，平台字段转换与 OneBot 专有操作留在接入层。

角色级与群级职责分别管理：Character 持有该角色的 Conversation；Conversation 管理平台连接与群会话；每个 ConversationLoop 独立持有 Planner 和 Replyer。提示词、模型窗口、规划历史与摘要由对应的 Planner / Replyer 管理，入口不组装模型上下文，loop 只处理调度、一轮业务流程与结果提交。

配置在首次显式调用加载函数时读取，进程内共用同一份配置快照。静态导入角色和模型模块不读取配置；chatModel、flashModel 保留直接导入的使用方式，供应商实例在实际请求时创建。

停止顺序：main 统一停止角色，Conversation 停止接收新事件，等待各群已接收的记录写入、当前轮次和后台压缩结束，再关闭平台连接。启动中收到停止信号时，先完成正在启动的角色的资源交接，不与 start 并发关闭同一连接。

### 会话与运行状态

会话由 `characterId + platform + channelId` 定位。不同角色或不同群的上下文相互隔离；同一角色的情绪、记忆、计划仍由对应角色模块共享管理。

每个会话维护：

- 真实聊天历史：收到的消息和实际发送成功的消息。
- 待处理消息：已收到但尚未交给本轮 Planner 的消息。
- Planner 上下文：此前输入、模型判断、工具调用和执行结果。
- Replyer 上下文：独立摘要与其覆盖位置之后的真实聊天记录，不保存旧的回复任务或 Planner 内部规划。
- 运行状态：是否正在处理一轮。
- 触发状态：待消费的定向触发标记、最近实际发言时间、连续不行动次数、退避等级与截止时间、下一次门控复查时间。
- 等待状态：Planner 选择的唤醒时间，以及等待背景。
- 压缩状态：Planner、Replyer 分别维护当前摘要、覆盖位置与压缩任务，进度互不绑定。

同一个会话串行处理，不同会话可以并行。Planner 或 Replyer 工作期间，新消息进入队列，不启动第二个并发轮次；本轮结束后，再对已到达的消息进行下一轮判断。

消息到达并不等于一定调用 Planner，调用 Planner 也不等于一定回复。程序负责触发时机，Planner 负责是否参与。

### 消息表示

聊天消息至少包含以下信息：

| 字段         | 用途                                              |
| ------------ | ------------------------------------------------- |
| `id`         | 平台消息 ID，用于引用和消息关联                   |
| `senderId`   | 平台用户 ID，不能用昵称代替身份                   |
| `senderName` | 展示给模型的称呼                                  |
| `timestamp`  | 消息时间                                          |
| `content`    | Satori XHTML 正文                                 |
| `quote`      | 可选的引用消息 ID、正文及平台实际提供的发送者信息 |

角色、平台和群身份由所属会话提供，不在上下文中为每条消息重复输出。引用单独保留，因为 Satori 的正文不包含被引用消息。

内部消息对象继续使用 camelCase 字段。提供给模型时，使用 Satori 构造完整 XHTML：普通消息为 `<message>`，属性包含 `id`、`sender-id`、`sender-name`、`time`、`is-self`；引用使用子元素 `<quote>`，正文保留原 XHTML 节点。戳一戳使用 `<poke>`，通过 `target-sender-id` 表示目标，不虚构消息 ID。`is-self="true"` 表示角色实际发出的事件，时间按项目时区展示为 `YYYY-MM-DD HH:mm 周几`。用户消息只能作为交流内容，不能被拼进系统规则。

XHTML 中存在媒体标签不代表模型已经理解媒体内容。Planner 按需调用 `understandMedia`，根据标签中的类型与 src 读取图片、音频或视频；取得理解结果前，不能把 URL 或标签当成已经完成的识别结果。

### 一轮交互流程

```text
收到 OneBot 事件
  → 确定角色，检查群白名单，过滤自身消息
  → 白名单通过后定位群会话
  → 转换消息，记录真实交流，加入待处理队列
  → 满足触发条件且当前无运行轮次时，取出本轮消息快照
  → 构建 Planner 上下文，调用 Planner
  → 得到聊天行动，或模型正常结束且未选择行动
      ├─ reply：调用 Replyer → 发送文字
      ├─ poke：按 senderId 确定目标人物 → 执行戳一戳
      ├─ wait：记录唤醒时间 → 结束当前调用，等待后续唤醒
      └─ 正常结束且未选择行动：消费本轮消息，更新沉默退避，继续旁听
  → 将实际发送的消息写入真实历史，将正文与执行结果反馈到 Planner 上下文
  → 释放本轮运行状态，按触发规则继续处理队列
```

### Planner 前置触发

确定实现独立的程序触发层。参考旧系统 `packages/message/src/chat/planner-replyer/trigger.ts` 与 `manager.ts`，以及 MaiBot 的消息触发设计：触发层判断当前是否值得投入思考，Planner 再决定是否行动，不为每条群消息调用模型，也不把进入 Planner 等同于必须回复。

消息先保存到历史和待处理队列，再评估是否触发；未通过门控的消息继续积累，之后按批次交给 Planner。

#### 触发路径与第一版参数

沿用旧系统的规则结构与数值作为第一版起点，阈值集中维护在 `conversation/trigger.ts`，暂不新增项目配置项。

| 路径         | 规则                                                                                                        |
| ------------ | ----------------------------------------------------------------------------------------------------------- |
| 定向触发     | 被 @、引用角色自己的消息、正文包含配置中的角色名称或昵称，直接获得一次 Planner 调用机会，绕过普通评分与退避 |
| 连续交流     | 角色实际发言后的 15 秒内，新消息直接获得一次 Planner 调用机会，沿用旧逻辑绕过普通评分与退避                 |
| 普通消息     | 综合内容、待处理消息积累和近期发言占比评分，总分达到 80 且不在退避期时触发                                  |
| 积累解除退避 | 待处理消息达到 6 条时解除退避，但仍需通过评分                                                               |
| 主动等待恢复 | Planner 的等待到期后，绕过普通门控继续判断                                                                  |

定向判断从 XHTML 中提取可见文本及明确的 @、引用身份，不对原始标签、URL 或属性做名称匹配。指向当前角色的戳一戳也走定向触发；只接收白名单群的事件，不将自身戳一戳回传当成外部事件。

普通评分沿用旧实现的基础项：

- 问题加 15 分，请求加 20 分，征询意见加 20 分。
- 可见文本长度达到 40 加 5 分，达到 120 再加 10 分；整批都是简短反应时，内容分改为 -25。
- 一条待处理消息的积累分为 50，多条按旧实现的对数公式增长，上限 100。
- 最近 5 分钟自己发言占比不超过 25% 时不扣分，达到 60% 时扣 25 分，中间线性变化。
- 这些规则只判断是否调用模型，不赋予角色助理职责，是否回应请求仍由 Planner 根据角色设定判断。

#### 沉默退避与定时复查

Planner 连续两次正常结束且未选择行动后，按 15、30、60、120、240、300 秒逐级退避。实际参与成功或选择主动等待时重置沉默退避；模型失败、输出截断或达到程序步数上限导致未完成判断，不能计为主动沉默。

旧系统的冷场加分比较的是最近两条外部消息之间的间隔，并非随当前等待时间持续增长；普通门控也没有独立的定时复查，因此最后一条未触发的消息可能长期留在队列中。新系统需要补上调度：

- 有未处理消息时，根据退避截止时间和冷场检查时间安排下一次门控复查；没有待处理消息时不安排复查。
- 每 30 秒复查门控；最早待处理消息每等待满 30 秒加 15 分，上限 30 分，替代旧的消息间隔加分。达到加分上限、退避结束后仍不触发，则停止复查，等新消息重新评估。
- Planner 已经判断并结束旁听的批次视为处理完成，不能定时反复拿同一批消息询问是否要说话。
- 退避到期不等于必然通过评分，必须按最新队列与历史重新判断。

门控暂缓与 Planner 主动等待分开维护：前者尚未调用模型，后者是模型主动选择稍后继续。唤醒统一受会话串行约束，定时器不能启动并发轮次。

#### 多群、角色状态与运行中的新消息

- 触发评分、关注窗口与退避按会话隔离，不引入跨群 Focus 竞争，保留同时参与多个群的能力。
- 角色睡觉或处于禁止聊天的场景时，只维护允许记录的交流内容，不触发聊天思考；定向触发不能绕过角色的聊天可用状态。具体状态读取随角色与场景模块接入，不用旧系统状态替代。
- 当前轮运行时，新消息只入队，定向标记保留给后续批次，不取消正在进行的 Planner 或 Replyer 调用。
- 一轮完成后对剩余队列重新评估门控；普通新消息并不保证立刻再调用一次 Planner。
- `trigger.ts` 负责定向判断和评分，`loop.ts` 维护运行状态、等待、退避与定时复查，不增加额外 LLM 触发判断。

严格按照角色配置中的 `onebot.group_white_list` 接收群消息，只接收群 ID 在白名单中的消息。白名单未配置或为空时，不接收任何群消息。检查在会话创建、消息存储与入队之前完成；白名单外的消息不进入聊天历史、不触发 Planner，@、引用或点名也不能绕过白名单。

### Planner

使用 `flashModel`，通过工具直接执行查询和聊天行为。同一轮可以戳一戳、回复多次，也可以正常结束、不采取行动；每次工具结果返回后继续判断。

| 工具          | 主要参数                                                                                     | 行为                                                                                                               |
| ------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `reply`       | `replyContext`、可选 `quoteMessageId`、可选 `sender-id`；`stickerIntent` 仅保留设计，暂不暴露 | 交给 Replyer 生成并发送文字，返回实际记录；传入 `quoteMessageId` 时引用对应消息，传入 `sender-id` 时 @ 对应的人 |
| `sendSticker` | `intention`                                                                                  | 定义独立表情回应工具，暂不实现执行逻辑、不加入当前可调用工具集                                                     |
| `poke`        | `sender-id`                                                                                   | 戳指定发送者，直接使用其平台用户 ID                                                                                |
| `wait`        | `seconds`                                                                                    | 等待 1～60 秒后再次判断                                                                                 |
| `understandMedia` | `media: { type: "image" \| "audio" \| "video"; url: string }[]`、可选 `instruction` | 查询所选媒体的内容，返回文字结果供后续判断 |

回复可以承接某个人、某句话或整个话题，也可以补充经历、表达感受或开启话题，不强制绑定一条目标消息。`replyContext` 必填，说明本次想表达什么、必要背景和交流对象；引用与 @ 是可选的发送方式，不是参与交流的前置条件。

移除 `targetMessageId` 和 `setQuote`，以可选的 `quoteMessageId` 指定引用消息，未传时不引用。工具中的发送者 ID 参数统一命名为 `sender-id`，与模型看到的 XHTML 属性一致；工具入口将其转换为业务对象的 `senderId`，内部发送代码不改名。`poke.sender-id` 必填，`reply.sender-id` 可选；未传时不添加 @，不从引用消息自动推导。引用与 @ 独立处理。

`reply` 工具内部调用 Replyer、发送并保存实际消息，`poke` 直接执行戳一戳。只有 `reply` 之间按到达顺序串行执行，覆盖生成、分段发送与记录；媒体查询、戳一戳不等待回复队列。每个工具独立收集并返回自己的实际执行记录。`wait` 设置暂停状态，当前步骤的工具（包括排队的回复）全部完成后停止后续模型步骤，由 loop 安排唤醒。

`understandMedia.media` 至少包含一个媒体，URL 使用 XHTML 中的 HTTP(S) 地址。按数组顺序下载媒体，通过现有 `getMultimodalModel` 选择支持本次全部输入类型的供应商；有指令时围绕指令理解，否则概述主要内容和可辨认的话语。回复依赖媒体内容时，先取得查询结果，再调用回复工具；Planner 在 `replyContext` 中传递相关事实与不确定之处。

多模态供应商的 `input_modalities` 只声明 `image`、`audio`、`video`。文本输入属于基础能力，不单独声明或参与筛选；例如 `["image"]` 表示支持图片及文本输入。

媒体二进制只进入本次多模态请求；Planner 历史保留工具参数和文字结果，按完整工具交互参与压缩。不新增媒体缓存或转码流程；下载、格式不支持或模型调用失败沿用现有工具失败处理。当前 OpenAI-compatible SDK 的音频输入支持 MP3/WAV，其他格式需要后续接入转码能力。

Planner 的输出上下文包含必要事实、主观立场和表达意图，不提前替 Replyer 写成品台词。不提供单独的结束工具，由程序根据调用结果判断：

- 调用聊天工具：当场执行，将工具结果交给模型继续判断。
- 模型正常结束：记录上下文并消费本轮消息；没有发送且没有工具失败时才更新连续沉默次数和退避状态，不发送模型的内部文本。
- 只调用了查询工具：提供工具结果并继续模型判断，不能把中间步骤视为旁听。
- 模型调用失败、输出截断或因程序步数上限而未完成判断：按规划失败处理，不计为主动沉默。

Planner 使用 `stopWhen` 与 `stepCountIs(20)`，最多 20 个模型调用步骤；`reply`、`poke` 不结束循环，模型正常结束或调用 `wait` 才结束本轮。达到步数上限仍需继续判断时按未完成处理。等待秒数为 1～60 的整数，不限制连续等待次数，不动态增减工具集合。等待期间普通消息入队，定向消息提前取消等待并绕过普通门控续接；等待到期即使没有新消息也继续判断。

#### 跨模块能力

尽量保留旧 Planner 的能力方向，但按新系统职责接入：

| 能力               | 新系统归属与接入条件                                   |
| ------------------ | ------------------------------------------------------ |
| 查询当前状态       | 角色模块提供主观状态，世界模块提供角色可感知的实际状态 |
| 查询人物画像与回忆 | 记忆模块提供，遵守角色隔离和遗忘范围                   |
| 查询物品、当前活动 | 世界模块提供受角色视角限制的查询                       |
| 提出计划变更       | 向当前负责决策的大脑提交请求，不由聊天直接改计划       |

这些模块目前尚未实现，第一轮不挂返回空数据的占位工具，不连接旧系统来补齐。跨模块工具随真实能力完成后加入；若要求本次全部可用，需要同步扩大实现范围。

### Replyer 与发送

使用 `chatModel`。输入按固定顺序由角色人设与通用回复规则、Replyer 历史摘要、摘要覆盖位置之后的真实聊天记录，以及本轮状态和 Planner 的 `replyContext` 组成；本轮指定了引用或 @ 时，同时提供对应消息或人物信息，不要求每次都有单条回复目标。

Replyer 使用追加式真实聊天历史，不每轮重新筛选“相关消息”或滑动截取最近 N 条。它与 Planner 共用真实聊天记录这一事实来源，但单独维护压缩摘要和覆盖位置，不复制保存另一套聊天事实。本轮回复任务放在请求末尾，不进入持久历史；实际发出的回复进入真实聊天记录。

每轮固定接收历史的边界，新到群消息留到下一轮。同轮后续回复可以看到之前已发出的消息，这部分先放在 Replyer 临时上下文尾部；轮次结束后再随完整历史参与压缩，避免摘要覆盖位置跳过尚未处理的新群消息。

Replyer 生成最终文字，不重新决定是否回复、不重新执行 Planner 的查询，也不能把未执行的打算表述成已完成事实。

输出文字通过 Satori 文本节点发送，不能直接把模型生成的普通文字当作可执行 XHTML。引用、@ 和图片节点由程序根据行动参数构造；@ 节点使用转换后的内部行动字段 `senderId`，不要求 Replyer 在正文中生成 @ 标签。

#### 分段与发送节奏

沿用旧应用 `packages/message/src/chat/planner-replyer/split-reply.ts` 的分段规则，由程序处理 Replyer 生成的完整文字，不增加 LLM 调用，也不要求模型输出分段数组。实现迁入新应用，不依赖旧业务包。

- 去掉首尾空白；不超过 24 个字符且不含换行的回复保持一段。长度按旧实现的 JS 字符串 `length` 计算。
- 保护 URL、匹配旧规则的英文数字连续片段，以及成对的中英文单双引号内容，不在这些片段内部切分。
- 换行和 `。！？；` 作为强分界；`，、` 只有在当前片段长度达到 18 时才作为分界。标点保留在前一段，换行不保留。
- 少于 4 个字符的片段并入前一段；第一段过短时并入后一段。
- 最多 3 段，超过时保留前两段，其余拼接为第三段，不截断正文。

发送节奏沿用旧应用 `packages/message/src/utils/message/delay.ts` 与 `sender.ts`：首段直接发送，后续每段按下一段文字长度等待，间隔为 `1000 + trim 后的长度 × 200 + 随机扰动` 毫秒；扰动约为 ±180 毫秒，最终限制在 400～10000 毫秒并取整。引用与 @ 仅附在第一条文字消息上。附带表情的发送节奏留到表情包逻辑实现时接入。

按实际成功发送的消息逐条记录，保留平台返回的消息 ID。沿用分段和间隔规则，不引入旧应用遇到新消息就取消当前发送的行为；新消息仍进入下一轮队列。

#### Planner 感知实际回复

执行反馈必须包含实际发送的正文、消息 ID、引用对象和 @ 对象，不能只返回“发送成功”。后续接入附带表情时也需反馈其结果。Planner 下一轮需要知道自己究竟说过什么，才能理解群友回应，避免重复或矛盾。

- 生成但未发出的内容不能记为已说过；部分发送成功时，只将成功部分记录为已发送。
- 戳一戳同样反馈实际执行结果；表情包实现后遵循相同原则。
- 自己发送的消息由本轮执行流程记录，不再次触发 Planner；平台回传不能造成重复记录。
- 工具通过 `return` 返回实际发送记录，由 SDK 生成 tool message，`onStepEnd` 保存完整调用与结果；不另行追加执行反馈，也不作为下一轮新群消息重复加入。
- 沉默和成功结束不额外追加反馈；`wait` 返回暂停结果，下次唤醒时再提供实际等待时间。
- 工具失败通过工具结果反馈简短事实，同时保留已成功部分，区分未发送、发送结果未确认，以及发送已确认但后续流程停止；存储失败不能描述成发送失败。模型请求失败只记录日志，不伪造工具结果。

### 上下文构建与 LLM Cache

两者都以稳定前缀和追加式历史组织请求。普通无状态 API 每次仍发送完整上下文，不能只发新消息并假定供应商记住了历史；服务端是否复用计算取决于模型、供应商及其缓存条件。

Planner 延续决策与执行过程：

```text
第一轮：[固定人设、规则、工具][消息 A、B][本轮状态]
第二轮：[以上原样保留][规划、工具与实际执行结果][新消息 C、D][本轮状态]
```

Replyer 延续真实交流，旧的回复任务不保留：

```text
第一次：[固定人设、表达规则][真实消息 A、B][回复任务 1]
第二次：[固定人设、表达规则][真实消息 A、B][实际回复 R][新消息 C、D][回复任务 2]
```

Replyer 第二次可以保留到消息 B 为止的相同前缀，不保证复用包含“回复任务 1”的后缀。压缩后，两者都在固定规则与近期历史之间放各自的历史摘要。

- 已有消息的呈现内容和边界保持稳定，不因新消息到来重新分组历史、更新旧昵称、重排 XHTML 属性或更换时间格式。
- 人设、规则与工具定义保持稳定，当前时间、情绪、活动等动态信息放在本轮末尾，不重写前面的系统规则。历史状态是当时的记录，不代表当前状态。
- 程序可以重新构造请求数组，关键是序列化后的历史内容与顺序一致，不要求复用同一个 JS 数组对象。
- 不为缓存无限保留历史，达到预算后再压缩旧前缀；替换摘要会使变化位置之后的缓存需要重新建立，固定前缀仍有复用机会。
- 分别记录 Planner、Replyer 的输入 token 和缓存命中 token，未返回缓存用量时不推断为已命中；不能用响应速度代替实际命中数据。

### 等待与新消息

选择 `wait` 后保存等待状态，用进程内定时器在到期时唤醒会话，不保持一个长时间等待的模型请求。

到期后，将等待期间的新消息、实际等待时长和等待背景交给 Planner。没有新消息时也需要再次判断，不能让等待变成永远不会结束的旁听。

普通新消息只入队，被 @、引用回复、叫到名字或收到指向角色的戳一戳时提前唤醒。提前唤醒时消费等待状态并取消旧定时器，避免同一次等待触发两轮。

生成回复期间的新消息按下一轮处理，当前方案不引入反复取消、重生成回复的机制。

### 表情包与戳一戳

- 本次只定义 `sendSticker` 的名称、描述和 `intention` 参数，不实现候选加载、模型选图、图片发送或资源配置。
- 工具定义暂不加入 Planner 的可调用工具集，不用空执行函数或伪造成功结果占位。`reply.stickerIntent` 保留为后续设计，当前请求 schema 暂不暴露，避免模型选择无法执行的附带表情。
- 后续实现独立表情回应与文字后附带表情时，再确定资源来源、配置与选择流程。
- 戳一戳通过 OneBot 的群戳一戳接口执行，成功结果记为内部行动结果，不伪造成文字消息。
- 接收白名单群中指向角色的戳一戳，作为定向事件触发 Planner，不伪造平台文字消息 ID。

### 提示词与人设

提示词定义集中维护在 `packages/shared/src/prompt/`。业务只调用 `renderPrompt(key, variables)`，模板系统首次使用时自动加载内置定义。

```text

```

人设 key 在通用前缀后追加配置中的角色 key，不使用名称或昵称。悠乃的角色 key 为 `yuno`，人设提示词 key 为 `character.persona.yuno`，显示名称为“悠乃”。

悠乃的人设写在代码中，Planner、Replyer 共用同一份人设。稳定事实沿用旧 `defaultCharacterPrompt`，通用聊天规则按新工具契约整理，世界背景不注入虚构的当前活动。

以后用户创建的角色人设可以存数据库，本次不实现。届时需要同时支持“覆盖内置 key”和“数据库独有的新 key”，不能要求所有角色 key 都先在代码中注册。当前不存在的人设应直接报错，不能套用悠乃的人设。

### 历史、持久化与压缩

真实交流和内部上下文分开维护：真实交流是发生过的事实；Planner 上下文包含内部判断、工具结果和实际发送反馈，服务后续推理。Replyer 使用真实交流构建上下文，并独立压缩。两者的上下文摘要都不自动等于长期记忆。

存储职责按以下方式划分；本次只定义查询与保存函数，不实现 MongoDB、Redis 的连接和读写逻辑：

| 内容                                                             | 存储         |
| ---------------------------------------------------------------- | ------------ |
| 真实聊天记录、实际发送的消息                                     | MongoDB      |
| Planner 上下文与处理位置、两者各自的摘要和覆盖位置、等待截止时间 | Redis        |
| 运行锁、模型请求、唤醒定时器                                     | 当前进程内存 |

在 `conversation/storage.ts` 中定义异步函数及明确的参数、返回类型，使用角色、平台、会话标识定位数据：

| 函数                        | 职责                                                            |
| --------------------------- | --------------------------------------------------------------- |
| `saveConversationMessage`   | 保存收到的或实际发送成功的消息                                  |
| `queryConversationMessages` | 按会话和记录范围查询真实聊天历史                                |
| `loadConversationState`     | 读取 Planner 上下文与处理位置、两者摘要与覆盖位置、等待截止时间 |
| `saveConversationState`     | 保存上述会话状态                                                |

接收记录与已发送记录共用会话内的串行写入队列，保证序号与提交顺序一致。收到的消息持久化成功后才进入历史和待处理队列；已发出的消息先写入真实历史和本轮快照，再持久化并通过工具返回结果，存储失败不能抹去外部事实。

前两个函数后续接 MongoDB，后两个函数后续接 Redis。具体记录结构随消息与上下文类型确定；collection、Redis key、查询分页和写入顺序留到持久化实现阶段明确。

每个函数体使用 `TODO` 注释标记应实现的 MongoDB 或 Redis 操作，并显式抛出未实现错误。不得返回空历史、空状态或伪造保存成功，也不以临时内存存储替代数据库实现。本阶段不接入自动恢复；依赖这些函数的流程在持久化补齐前不算已完成可运行的闭环。

恢复时不能只加载最近聊天记录而丢失 Planner 的处理位置，也不能把发送结果不明的任务直接重新发送。重启后是否恢复等待、如何处理未完成轮次，需要在持久化实现前确定。

上下文压缩沿用已有低延迟方案：

1. Planner 与其压缩使用 `flashModel`，Replyer 与其压缩使用 `chatModel`。分别根据各自窗口提前启动后台压缩，每个会话的每类上下文最多一个压缩任务，进度互不绑定。固定前缀和历史呈现保持一致，压缩指令追加在末尾，不执行行动工具；实际缓存是否命中由供应商决定。
2. 固定压缩范围，将对应的旧摘要和较旧的完整记录整理为新摘要。
3. 压缩期间继续处理消息，新增记录保持在压缩范围之外。
4. 成功后在下一次模型调用前替换摘要，保留覆盖位置之后的全部记录。
5. 每次请求前估算上下文：Planner 在 70% 启动后台压缩、85% 等待压缩；Replyer 在 50% 启动后台压缩、70% 等待压缩。低于各自等待阈值时前台可继续；达到阈值则等待已有任务或执行压缩。应用摘要后重新估算，仍达等待阈值则继续整理尚未覆盖的旧内容。压缩失败、摘要未缩短上下文或没有可压缩内容时停止本次生成，不无限重试、不静默截断历史。

两套摘要使用独立提示词，输出自然语言正文：

|          | Planner                                                        | Replyer                                              |
| -------- | -------------------------------------------------------------- | ---------------------------------------------------- |
| 压缩内容 | 群聊、规划、工具调用与实际行动结果                             | 真实群聊和实际发送的回复                             |
| 保留重点 | 当前参与意图、必要判断依据、未完成事项、已表达的立场与行动结果 | 话题进展、人物指代、双方说过什么、必要原话与表达语境 |
| 不保留   | 冗长推理与无关工具细节                                         | 旧回复任务和 Planner 内部规划                        |

#### 近期原文与压缩边界

两者都保留近期原文，不将全部历史替换成摘要，也不直接按最后 N 条 `ModelMessage` 截取。

- Planner 按输入、完整模型交互依次追加上下文单位，执行反馈属于对应工具交互，不额外追加消息。使用独立交互序号，一轮可以包含多个单位；每次模型请求前应用已完成摘要并检查窗口。
- 同一条 assistant 消息中的多个工具调用，必须与全部对应结果一起保留或压缩，按工具调用 ID 对齐，不能留下孤立的调用或结果。
- 同一轮中已经完成的交互可以参与压缩，正在执行的工具交互不能拆分。工具全部结束后，通过 SDK 的 `onStepEnd` 一次记录该步调用与结果；`prepareStep` 等待必要压缩并返回重建后的请求，不重放已执行工具、不重置本轮发送进度。
- Replyer 当前没有工具调用，以完整真实聊天消息为边界保留近期原文，本轮回复任务不进入历史。
- 后台任务开始时固定覆盖位置；完成后只替换此前确定的旧前缀，不能重新按消息条数切分，也不能覆盖期间新增的内容。
- 最近原文保留量按约 10% 窗口向完整交互边界取整，至少保留一个单位；若单个不可拆交互过大，不能通过截断调用或结果满足预算，应报告无法继续。

```text
Planner 一轮中的上下文单位：
输入单位：本轮输入
交互单位 1：assistant 调用工具 A、B + tool 返回 A、B 全部结果
交互单位 2：assistant 调用 reply + tool 返回实际发送记录或简短失败事实
交互单位 3：assistant 正常结束本轮

单位 1 完成后即可与更早历史一起参与压缩，不必等待业务轮次结束。
压缩后的上下文：固定规则 + 历史摘要 + 近期完整交互 + 最新输入
```

本次模型请求使用固定历史快照，压缩和消息到达都不能改变已经发出的请求。替换摘要只改变对应模型的上下文，不删除共享的真实聊天记录，也不替代最新状态。

进程内历史只保留未处理消息、Replyer 摘要尚未覆盖的原文和最近 5 分钟的触发评分记录。旁听时也维护 Replyer 摘要；正在执行轮次时，新消息的摘要维护延后到轮次结束，不能进入当前轮的快照。移出内存的消息仍由 MongoDB 保存，选中旧消息引用时按平台消息 ID 查询原文，仅放入当前回复任务，不重新插入历史前缀。数据库分页和重启恢复仍留待持久化阶段实现。

压缩直接以对应模型组的 `context_window_tokens` 为基准：Planner 的后台压缩 / 等待阈值为 70% / 85%，Replyer 为 50% / 70%；达到等待阈值时阻塞下一次请求。两者均保留约占窗口 10% 的近期原文，按完整交互/消息边界向外取整。估算仍沿用 UTF-8 字节数的保守粗估，并非真实 token 数。压缩请求本身也受窗口限制，过长时按完整交互分批推进覆盖位置；只有确实缩短上下文的摘要才会替换旧前缀。计入固定提示词、工具定义、摘要、历史和本轮输入，不单独计算或扣除输出预留，也不增加相关配置。输出上限使用已有 provider request 配置或供应商默认值，业务层不额外设置固定上限。

### 失败处理与可观察性

- LLM 供应商切换和冷却复用 shared 能力，聊天层不再额外套一层相同重试。
- 规划、生成、发送失败都记录对应阶段；释放会话运行状态，不能因异常导致后续消息永久无法处理。
- 只把确认成功的外部操作记录为成功；部分发送成功时保留已发送事实，不重发整轮。
- 平台请求结果不确定时，不自动重试发送，避免重复回复或重复戳一戳。
- 日志包含角色、会话、阶段、耗时、模型用量和执行进度，复用现有 logger。
- 工具失败以工具结果交给模型继续判断。轮次结束时，若发生失败且整轮尚未尝试发送，保留未完成批次，等待下一次外部事件后合并重新判断，不计为沉默，不用冷场定时器循环重试。只要本轮已经尝试平台发送，即使后续模型调用失败也消费当前批次，不重发整轮；显式等待则按等待状态续接。
